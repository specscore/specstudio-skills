**Supersedes:** —

## Problem Statement

How might we turn an approved SpecScore Plan into focused, AC-traceable commits — without losing human-in-the-loop control and without re-inventing the TDD process skills that already exist?

## Context

SpecStudio today ships four lifecycle skills: `init`, `ideate`, `specify`, and the newly-shipped `plan`. `plan` produces a lint-clean `spec/plans/<slug>.md` whose tasks each declare a `**Verifies:**` line listing the AC IDs they satisfy. The next step — actually writing the source code that makes those ACs pass — has no SpecStudio skill yet. Users fall back to general-purpose implementation skills (`agent-skills:test-driven-development`, `agent-skills:incremental-implementation`, `superpowers:test-driven-development`, `superpowers:executing-plans`) that have no awareness of the Plan's AC linkage. As a result, commits don't reference the ACs they satisfy, partial implementations are hard to detect, and the spec↔code coherence loop breaks at the implementation step. The placeholder Feature at `spec/features/skills/implement/README.md` captures the intent but explicitly defers the design to this Idea.

A separate concern surfaced inside this repo's own ideation flow and is folded into this Idea: for Features small enough that their Plan's task bodies become paraphrases of the diff, users feel the plan→implement step as duplication of work. This Idea captures the design for a **stub-plan posture** that lets `implement` write the task-body narrative as a journal during implementation rather than requiring it to be authored before approval. Stub-plan support ships **in the MVP alongside the default `full` posture** — folding it in saves a second plan-Feature revision cycle, a second implement-Feature spec cycle, and a second round of approvals, at the cost of a slightly larger single spike (4–5 weeks instead of 2–3). The writeback contract is fundamentally an `implement`-side concern, so designing it once here (rather than splitting across a separate Idea) avoids drift.

## Recommended Direction

Ship a **parallel-dispatching orchestrator** `specstudio:implement` that mirrors the discipline of `ideate`, `specify`, and `plan` (same gate-then-act shape, same auto-stage-on-create staging-only pattern, same honest-pushback tone) while adopting the parallel-subagent execution model proven by `superpowers:subagent-driven-development` and `agent-skills:subagent-driven-development`.

The skill reads an approved Plan, computes the task dependency graph (from the new `**Depends-On:**` annotations the `plan` Feature gains as a coupled revision), and dispatches one subagent per task in the next executable batch — that is, all tasks whose dependencies are satisfied. Each subagent receives: the task description, the source Feature's relevant ACs in `Given / When / Then` form, the mandatory `Verifies: <feature-slug>#ac:<ac-slug>, …` commit-message-trailer convention, and the project's TDD discipline (delegated to `agent-skills:test-driven-development` / `superpowers:test-driven-development` when available, or a minimal direct in-skill TDD flow as fallback). Subagents stage their changes via `git add` and return a summary; they do not commit. When all subagents in the batch return, `implement` presents a consolidated staged diff plus a draft commit-message template to the user, who reviews and decides on commit shape (one commit per batch, one per task, or any split they prefer). On user approval, `implement` advances to the next executable batch.

**Staging-only, not committing**, matches the upstream skill pattern: the user owns commit shape (branch, message wording, granularity, signing), composability with adjacent edits is preserved, multi-commit refinement remains possible, and the `Verifies:` trailer is delivered as a *structured commit-message template the user pastes* rather than a skill-executed `git commit`. The AC-linkage guarantee becomes a lint-enforceable convention (a future `commit-msg` git hook can validate the trailer references valid AC IDs) — a stronger discipline than "the skill ran commit, trust it."

Task progress is tracked via two sources: the per-task `**Status:**` body-metadata field on the Plan (written by `implement` as subagents progress — see "Per-task status tracking" below) and a git-log scan for `Verifies:` trailers in commit messages. The git-log scan is *authoritative* (a real commit referencing an AC is ground truth); the Plan's `**Status:**` field is the at-a-glance signal cross-checked against git on every invocation. On ambiguous ACs a subagent stops, returns a structured "needs clarification" report, and `implement` surfaces it to the user with a recommendation to invoke `specstudio:specify` for revise-in-place before continuing.

This design closes the spec↔code coherence loop at exactly the handoff where it matters most, takes full advantage of subagent parallelism for genuinely independent tasks (the common case for well-decomposed Plans), and keeps the gate discipline familiar to anyone who has used the upstream skills. The speculative directions (remote runner dispatch for cross-machine execution, autonomous multi-batch loops without per-batch user approval) remain as follow-on Ideas.

**Plan posture (in MVP).** Each Plan declares a posture via a `**Mode:** <full|stub>` body-metadata line, defaulting to `full` if absent. **Full** mode is the default execution model above — task bodies fully authored before Plan approval, subagents receive the authored body verbatim as part of their prompt. **Stub** mode lets the user approve a Plan whose task bodies are a single placeholder marker; `implement` then journals what landed back into each task body after the batch completes. Subagent contract differs by posture: in `full` mode the subagent receives the authored task body; in `stub` mode the subagent receives the task name + `**Verifies:**` ACs + `**Depends-On:**` + the Plan's `## Approach` section, and generates its own implementation approach from the ACs. Posture is user-declared explicitly at `plan` time — no AC-count auto-classification, no LLM-classifier guess. Once a Plan is `stub`, it stays `stub` for its lifetime; no mid-flight re-classification in this Idea (revisit on observed need).

**Per-task status tracking (both postures).** Each Plan task additionally has a `**Status:**` body-metadata field (`pending` / `in-progress` / `done` / `blocked`), default `pending`. `implement` updates this field as subagents progress: `pending → in-progress` on dispatch, `in-progress → done` on subagent DONE (or `→ blocked` on BLOCKED). Status writes apply to **both** full and stub plans — full plans don't get body writeback but do get status updates. Status is the at-a-glance progress signal in the rendered Plan; the `Verifies:` commit-message trailer (parsed via git log) remains the *authoritative* progress source and is cross-checked against the Plan's status fields on every invocation.

**Writeback trigger (stub posture).** When all subagents in a batch return, `implement` writes back to the Plan file as part of the same staging operation as the code changes — Plan.md and the touched code files all land in one `git diff --staged` for the user's review, and the user commits them atomically as one commit. This minimizes user involvement: no separate "approve the journal entry" step, no placeholder SHAs to reconcile post-commit, no two-phase commit dance. The per-batch commit therefore contains both the code that satisfies the batch's ACs and the Plan journal entries (one short paragraph per task) that describe what landed. The `plan.updated` event fires once per batch on successful commit.

## Alternatives Considered

- **Strict one-task-at-a-time linear execution.** Load task 1, do it, confirm, load task 2, do it, confirm, …, repeat. Considered as the safest MVP. Rejected: confirmation-per-task across a 12-task Plan is bureaucracy dressed up as discipline; `superpowers:subagent-driven-development` and `agent-skills:subagent-driven-development` have already proven that parallel subagent dispatch is the right tool for independent tasks; and the "code is never written autonomously" principle from `sidekick-ideas.md` is about *the spec↔plan gates*, not about per-task confirmation during execution of an already-human-approved Plan. The right gate is "user approves the batch's consolidated diff," not "user approves each task individually." Linear-only execution remains available as a *consequence* of dependency annotations (a fully-sequential dependency chain produces single-task batches), but it's not the *default*.
- **Skill commits on user confirm (departing from staging-only).** Originally proposed as "the commit IS this skill's artifact, justifies the departure." Rejected: rhetoric, not architecture. Every upstream skill's artifact also eventually lives in a commit; that framing doesn't distinguish `implement`. The actual reasons for staging-only — user owns commit shape (branch, message, granularity, signing), composability with adjacent edits, multi-commit refinement, diff inspectability before the point of no return, failure recovery, branch neutrality — all apply equally to `implement`. The AC-linkage guarantee can be delivered via a structured commit-message template the user pastes (and, optionally, a future `commit-msg` git hook that lints the trailer) — a stronger discipline than the skill executing `git commit`.
- **Autonomous multi-batch worker (no per-batch user approval).** Run all batches end-to-end: dispatch batch 1, all subagents return, auto-stage, auto-commit, dispatch batch 2, … without user intervention until the Plan is fully implemented. Rejected: this *is* the case `sidekick-ideas.md` warns against — autonomous code generation. The per-batch user-approval gate is the human checkpoint that keeps the line honest. Future Phase 2 could lower this to "auto-advance through batches with consolidated diffs surfaced at end" but that's a separate Idea once we've observed adopters' tolerance for the per-batch cadence.
- **remote runner dispatcher.** Skill is purely a queue producer: enqueues each task as a `synchestra task` of type `implement`, lets a remote runner pick it up and execute. The skill itself doesn't write code. Rejected *for MVP*: requires remote runners to exist (they don't), couples the plan format to a dispatch protocol that hasn't stabilized, and adds an asynchronous layer where every iteration is now distributed-systems debugging. Worth revisiting as a separate Idea once the runner abstraction lands.
- **Pure helper, zero code-writing or dispatch.** Skill loads the next task and shows the user: "Here's task N, here are its ACs, here's the commit-message template — write the code and ping me when you're done." No subagent dispatch, no in-skill TDD. Rejected: this is roughly what disciplined users already do today; the only value-add is structured task loading. The point of a SpecStudio skill is to *enforce* a contract and to take work off the user's plate — a pure helper does neither.
- **Per-task SKILL.md generator.** For each Plan task, dynamically generate a task-specific instruction file at `skills/implement/_tasks/<task-n>.md`, then hand back to the user to invoke. Rejected: defeats the purpose — we'd be generating ad-hoc skills instead of running the orchestration. Also fragments the skill surface in confusing ways.
- **Stub-plan posture as a separate Idea / separate skill / phase-2 follow-on.** Considered (the parallel session originally proposed Phase-2 sequencing). Rejected: the writeback contract — what `implement` writes back, when, in which event, under what concurrent-edit semantics — is fundamentally an `implement`-side design. A separate "stub plans" Idea would have to specify the same contract from the Plan-artifact side and risk drift. Folding into one MVP also saves a second plan-Feature revision cycle, a second implement-Feature spec cycle, and a second round of approvals — net cost lower than ~30% even with the larger spike. Risk: stub-mode design is more speculative than full-mode (no full dogfooding feedback before stub is locked in); mitigated by keeping both postures' MVP scope minimal and revising additively if observed need diverges.
- **Make every Plan stub by default; remove pre-authored task bodies entirely.** Rejected. The pre-authored task body is a forcing function for medium-and-larger Plans: it forces the planner to articulate decomposition before code is written. Removing it across the board loses that discipline. The right shape is `full` as default, `stub` as opt-in posture.
- **Gate-inversion for trivial cases (plan becomes a post-condition of implement, not a pre-condition).** Considered as an alternative to stub-plan posture. Rejected: inverting the gate creates two parallel mental models (pre-condition for normal cases, post-condition for trivial cases) and a classification problem (when does the inversion apply?) that costs more than the duplication it removes. Stub-plan posture keeps the gate intact (a Plan still exists and lints before `implement` runs) while removing the duplication that motivated the concern.

## MVP Scope

A four-to-five-week spike: implement `specstudio:implement` as a single skill folder under `skills/implement/`, mirroring `skills/plan/` in structure. Land the coupled `plan` Feature revision *first*, then build `implement` on top.

The coupled `plan` Feature revision (single revise-in-place pass, additive in every direction) adds: (a) `**Depends-On:**` task body field (default `—`) for the dependency graph; (b) `**Status:**` task body field (`pending` / `in-progress` / `done` / `blocked`, default `pending`) for per-task progress tracking; (c) `**Mode:** <full|stub>` Plan body-metadata line (default `full` when absent); (d) permission for task bodies to be a single placeholder marker (token TBD — see Outstanding Questions) when the Plan's mode is `stub`; (e) lint rule `P-003` for cycle detection; (f) lint rule `P-004` preventing placeholder bodies in `stub` Plans for tasks whose Status is `done`; (g) reviewer-baseline blocker updates (cycle detection, stale Depends-On task numbers, placeholder bodies in wrong contexts).

Dogfood `implement` on `implement`'s own Plan once `specify` and `plan` produce one — the dependency graph for the skill itself will exercise both linear-chain and parallel-batch cases, and the Plan can be authored in either posture to test both. Ship it, observe whether the per-batch confirmation cadence + consolidated-diff format + dual-posture support earn their keep, and stop.

MVP excludes: remote runner dispatch, autonomous multi-batch loops without per-batch approval, branch / worktree management, conflict resolution beyond detection-and-rollback, mid-flight posture re-classification, and AC-count auto-classification of posture. If the artifact isn't embarrassingly minimal on day one, it waited too long — and "embarrassingly minimal" here means "full posture is fully working and stub posture is fully working; both are simple."

## Not Doing (and Why)

- Autonomous multi-batch execution without per-batch user approval — every dispatched batch's consolidated diff goes through a user-approval gate before the next batch dispatches; matches the "code is never written autonomously" principle from `sidekick-ideas.md` applied at the *batch* checkpoint rather than the per-task one.
- Reinventing TDD — `implement` is an orchestrator and parallel dispatcher, not a TDD engine; subagents delegate the actual code-writing discipline to `agent-skills:test-driven-development` / `superpowers:test-driven-development` or a minimal in-skill fallback.
- Committing on the user's behalf — `implement` stages via `git add` and provides a structured `Verifies:` commit-message template; the user runs `git commit` themselves, preserving full control over commit shape (branch, message, granularity, signing). Matches the staging-only pattern of `ideate` / `specify` / `plan`.
- Branch / worktree / merge management — the user's call; `implement` stages on the current branch.
- Per-task status mutation of the Plan schema **beyond what's necessary for the four-state Status field**. The MVP adds a `**Status:** <pending|in-progress|done|blocked>` task body field; it does **not** add richer status (e.g., reviewer-approval state, owner assignment, time-spent). The git-log scan for `Verifies:` trailers remains the *authoritative* progress source; the Plan's Status field is the at-a-glance signal and is cross-checked against the git log on every invocation.
- remote runner dispatch (cross-machine execution) — premature; couples to infrastructure not yet built. Separate follow-on Idea. *Local* subagent dispatch via the Claude Code / agent-skills / superpowers subagent mechanism is the MVP execution model.
- Code review — `specstudio:review` is the right skill for that, downstream of `implement`.
- Test execution beyond what the delegated TDD process produces — `specstudio:verify` runs the full Rehearse scenario sweep downstream.
- Cross-Plan or roadmap-level implementation — single Plan per invocation, mirrors `plan`'s single-Feature scope.
- Conflict resolution between sibling subagents' diffs beyond detection-and-rollback — if two parallel subagents produce diffs touching the same lines, the MVP surfaces the conflict to the user and rolls the batch back; smarter merge logic is a follow-on.
- **Auto-classification of Plans as `stub` vs `full`** — posture is user-declared explicitly; no AC-count heuristic, no LLM classifier, no skill-side guess. Auditability beats convenience. (Consilium's "decide if plan can be autowritten" role may overlap with posture suggestion — see Outstanding Questions — but that is at most a *recommendation*, not an *imposition*.)
- **Body writeback to `full` Plans** — the body-writeback path (post-batch journal entry replacing a placeholder marker) runs only for `**Mode:** stub` Plans. `implement` does not write task *bodies* in `full` Plans (their bodies were authored at plan time). `implement` *does* write task `**Status:**` in full Plans — status updates apply to both postures. The user MAY also manually edit any full Plan field; `implement` simply does not author body edits itself.
- **Mid-flight posture switching** — once a Plan is `**Mode:** stub`, it stays stub for its lifetime; once `full`, it stays full. No `--switch-mode` flag, no automatic switching, no protocol for handling already-written-back bodies on switch-to-full. Revisit on observed need.

## Key Assumptions to Validate

| Tier | Assumption | How to validate |
|------|------------|-----------------|
| Must-be-true | AC-to-commit linkage is the actually-painful gap, and users will accept a per-batch confirmation gate in exchange for traceability. | Dogfood on `implement`'s own Plan; ask two external early users to run `implement` on an approved Plan and report whether the per-batch consolidated-diff cadence felt valuable or annoying. Kill the skill if the gate is universally felt as friction. |
| Must-be-true | Parallel subagent dispatch via the available subagent mechanism (`general-purpose` agent type, dispatched via the Agent tool) is reliable enough at MVP scale — N concurrent subagents complete, return summaries, and stage their changes without conflicting with each other except in cases the dependency graph predicts. | Implement a batch with 3–5 parallel subagents on independent tasks; verify no spurious conflicts, no lost staging, no subagent context-overflow failures. Cap max-parallel at 5 in MVP and adjust based on observed cost / reliability. |
| Must-be-true | The `plan` Feature can be revised additively to add `**Depends-On:**` task annotations without breaking existing Plans — a Plan without `**Depends-On:**` lines defaults to a fully-sequential chain (current linear semantics preserved). | Revise the `plan` Feature via revise-in-place; verify the existing approved Plan for `sidekick-consilium` still lints clean and runs correctly through `implement`. |
| Should-be-true | Tracking task progress via git log scan for `Verifies:` trailers is sufficient — no per-task status field needed on the Plan schema. | Implement one Plan with `implement`; on subsequent `implement` invocations, check that the skill correctly identifies the next executable batch without false positives or false negatives. If git-log scan misses cases, escalate to a per-task `**Status:**` field on the Plan and update the `plan` Feature additively. |
| Should-be-true | Conflict detection between sibling subagents' diffs (line-level overlap check after a batch completes) catches all real conflicts at MVP scale; no silent merge corruption. | Construct a deliberate-conflict scenario in a test Plan (two tasks both edit the same function); verify detection catches it and rollback restores the worktree to pre-batch state. |
| Should-be-true | Staging-only with a structured `Verifies:` commit-message template is the right ergonomic, mirroring the upstream skills — the user wants control over commit shape and is fine writing the commit themselves once the message is pre-baked. | Two adopters, two weeks: do they reach for the template, or do they ignore it and write commit messages from scratch? If they ignore it, the template format is wrong; iterate. Also worth revisiting whether `implement` should optionally commit (opt-in `--commit` flag) if adopters consistently prefer the autocommit ergonomic. |
| Might-be-true | Future `verify` and `review` skills will hook into the same `Verifies:` trailer convention, completing the chain commit ↔ AC ↔ REQ ↔ Feature ↔ Plan. | Defer validation until `verify` is designed; design `implement`'s trailer format to be parseable in isolation so the future skills can adopt without coordination. |
| Might-be-true | When the source Feature's ACs drift after a Plan is approved (e.g., the user revises the Feature mid-implementation), `implement` can detect and surface the drift, redirecting the user to `specstudio:specify` and a fresh `specstudio:plan`. | Defer until the first observed drift incident in dogfooding; design the AC-resolution step in each subagent to fail loudly on stale references rather than silently fall through. |
| Should-be-true | A meaningful share of Plans authored against this repo (and other dogfood projects) benefit from `stub` posture — enough to justify shipping it in the MVP alongside `full`. If <15% of Plans elect `stub` after a month of MVP availability, deprecate the posture and remove the writeback path in the next revision. | Tag each dogfood Plan with its posture choice; review after 10 Plans. Posture-choice telemetry is captured implicitly via the `**Mode:**` body metadata line. |
| Should-be-true | The writeback contract (post-batch, replace placeholder, restage Plan file, emit `plan.updated`) doesn't introduce data races with concurrent user edits to the Plan — `implement` and the user don't fight over the same task body's text under any realistic interleaving. | Stress-test: deliberately edit the Plan's Summary or Approach section while `implement` is mid-batch in `stub` mode; verify the writeback only touches task bodies for tasks in the just-completed batch and surfaces a conflict if a Plan-file edit by the user would be overwritten. |
| Might-be-true | Consilium's existing role ("decide if a plan can be autowritten to speed up overall process at cost of tokens") overlaps with "this Plan should start in `stub` posture" — they may unify into a single posture-recommendation pass at `plan` time, with consilium making the call. | Defer until MVP is in flight; check whether the two decisions reduce to one. If they do, the user-declaration-only rule above relaxes to "consilium recommends, user confirms." |

## SpecScore Integration

- **New Features this would create:** One — the `implement` skill Feature itself, replacing the placeholder at `spec/features/skills/implement/README.md`. Cross-cutting Features that *might* spin off (commit-message `Verifies:` trailer schema, task-progress git-log query, subagent dispatch contract) are likely to live as REQs inside this Feature rather than separate Features in the MVP.
- **Existing Features affected:** `spec/features/skills/plan/README.md` requires a single **revise-in-place revision** as a coupled prerequisite — additive in every direction (existing approved Plans without any of the new fields continue to lint and run unchanged). The revision adds, in one pass: (a) an optional `**Depends-On:**` body field on each `### Task N:` block (value `—` for no dependencies, or a comma-separated list of predecessor task numbers); (b) a `**Status:**` body field on each task block (`pending` / `in-progress` / `done` / `blocked`, default `pending`); (c) a `**Mode:** <full|stub>` Plan body-metadata line (default `full` if absent); (d) permission for task bodies under `### Task N:` to be a single placeholder marker (exact token TBD — see Outstanding Questions) when the Plan's mode is `stub`; (e) softening of the current `REQ: linear-presentation-numbering` to allow declared dependencies — tasks remain numbered linearly (presentation order) but their execution order is determined by the dependency graph (a default `**Depends-On:** —` on every task collapses to current linear semantics, preserving backward compatibility); (f) lint rule `P-003` for cycles in the dependency graph; (g) lint rule `P-004` preventing placeholder bodies in `stub` Plans for tasks whose Status is `done`; (h) updated reviewer-baseline blocker categories to include cycle detection, stale-task-number references in `**Depends-On:**`, posture-inconsistent placeholder bodies, and Status values inconsistent with the git-log `Verifies:` cross-check.
- **Dependencies:** **Blocking:** the `plan` Feature revision above MUST land before `implement` ships, because `implement`'s parallel-dispatch logic reads the dependency graph from Plan tasks. Non-blocking but helpful: (a) a `specscore code` subcommand or equivalent that scans git log for `Verifies:` trailers (would speed up the "find next executable batch" lookup; the MVP shells out to `git log --grep` instead); (b) `agent-skills:test-driven-development` / `superpowers:test-driven-development` skills available in the user's environment (the in-skill TDD fallback covers the no-skills case).

## Open Questions

- **Commit-message trailer format.** The Idea posits `Verifies: <feature-slug>#ac:<ac-slug>, <feature-slug>#ac:<ac-slug>` as the trailer. Is `Verifies:` the right keyword, or should it be `AC:`, `Satisfies:`, or `Implements:`? Should the trailer follow the Conventional Commits trailer convention (footer block, blank line separating, `Key: value` shape) or be a plain inline tag? Resolve at spec time.
- **TDD-skill detection / delegation.** Should each `implement`-dispatched subagent actively detect whether `agent-skills:test-driven-development` or `superpowers:test-driven-development` is installed and invoke it via the Skill tool from inside its own context, or just receive the AC contract and let the subagent's default behavior produce code? Active invocation is cleaner but couples to those skills' public surfaces; passive delegation trusts the subagent's prompt.
- **Subagent prompt / context shape.** Each subagent needs: the task description, the source Feature's relevant ACs in `Given / When / Then` form, the `Verifies:` trailer convention, the project's TDD discipline pointer, and a stop-and-report-back contract on AC ambiguity. The exact prompt template is spec-time work — should be designed so it works against `general-purpose` agent type without requiring a custom subagent type.
- **Max-parallel-subagents cap.** MVP proposes capping at 5 concurrent subagents per batch to control context cost. Should this be configurable per project (in `specscore.yaml`)? Spec-time decision; defaults sit in the skill.
- **Partial-failure batch semantics.** If 3 of 5 parallel subagents return success and 2 fail (test failure, AC ambiguity, context overflow), what does `implement` do? Three options: (a) present the 3 successful staged diffs to the user for partial-batch approval + retry the 2 failures; (b) roll the whole batch back, treat as atomic; (c) per-failure decision with the user. MVP recommendation: (a), because the 3 successful tasks are independent contracts — but the spec should make this explicit.
- **Conflict detection method.** Post-batch line-overlap check via `git diff --staged` is the MVP approach. Should it also detect *semantic* conflicts (two subagents both implementing the same feature differently in different files)? Probably out of scope for MVP — line overlap catches the worst cases; semantic-conflict detection is a future Feature.
- **Git-log task-progress lookup performance.** For a Plan with N tasks and a repo with M commits, the "find next executable batch" query scans M commits for `Verifies:` trailers. For typical M (hundreds), `git log --grep` is fine. For long-lived repos (tens of thousands), it might be slow enough to want an index. Resolve only if dogfooding actually hits the slow case.
- **Ambiguous-AC handoff protocol.** When a subagent stops on an ambiguous AC, does `implement` (a) self-terminate the whole batch and let the user re-invoke after specify completes, (b) cancel just the ambiguous subagent's task and let sibling subagents finish, or (c) wait for user clarification inline? Each has cost tradeoffs; spec-time work.
- **Source Feature change during implementation.** If the source Feature's ACs change while `implement` is mid-Plan (e.g., the user adds a new AC to the Feature, which the existing Plan doesn't cover), does `implement` detect and surface the drift between batches, or does it ignore Feature changes until the user re-runs `plan`? Detect-and-surface is the safer default; defining the exact protocol is spec-time work.
- **Plan posture declaration syntax.** A Plan body metadata line `**Mode:** stub` (defaulting to `**Mode:** full` when absent) is the natural fit, but should posture also be settable via a `--mode=stub` flag on `specstudio:plan` invocation, with the body metadata derived from the flag? Or both? Spec-time decision; recommendation: support both (CLI flag writes the metadata line; if both differ on revise-in-place, the file wins).
- **Placeholder token format for stub-mode task bodies.** Candidates: `<!-- implement: pending -->` (HTML comment, invisible in rendered markdown, machine-friendly), `**Implementation:** _pending_` (visible, scannable in a rendered Plan), or `_to be journaled by `implement`_` (visible, self-documenting). Visibility-vs-noise tradeoff; spec-time decision.
- **`plan.updated` emission cadence in stub mode.** The writeback-trigger answer (bundled with code staging, one commit per batch) implies one `plan.updated` per batch on successful commit. Confirm at spec time and document the payload's `changed_sections` discipline (every batch's `plan.updated` should list the task slugs whose `**Status:**` or body changed).
- **Concurrent-edit semantics during writeback.** If the user manually edits a task body in a `stub` Plan (or any field in either posture) while `implement` has a batch in flight, what wins? Pre-batch staging of the Plan file by `implement` (so the user's edits visibly conflict at `git add` time) is the safest option; spec-time decision.
- **Consilium overlap with posture recommendation.** Does the consilium skill's "decide if a plan can be autowritten" judgement reduce to a posture recommendation (recommend `stub` when consilium would have autowritten)? If yes, the user-declaration-only rule relaxes to "consilium recommends, user confirms." Spec-time work; the implement Idea makes no commitment.
- **Status field cross-check semantics.** The Plan's per-task `**Status:**` and the authoritative git-log `Verifies:` trailer scan can disagree (e.g., a manual `git commit` referenced an AC but `implement` didn't write a Status update; or the Status was edited manually). Which wins, and how is the disagreement surfaced? Recommendation: git-log is authoritative on `done`; the Plan's Status field is informational and `implement` reconciles it on every invocation, surfacing any divergence to the user as a warning.
