# Idea: Retrofit Skill — Specifications for Existing Spec-less Projects

**Status:** Draft
**Date:** 2026-05-22
**Owner:** alex
**Promotes To:** —
**Supersedes:** —
**Related Ideas:** —

## Problem Statement

How might we let teams adopt SpecScore on a codebase that already exists by deriving Feature specs from the code, tests, and docs that are already there — without forcing a from-scratch rewrite of intent?

## Context

Every existing specstudio skill assumes you start with an Idea and move forward to code (ideate → specify → plan → implement → verify → recap). But the overwhelming majority of real-world projects already ship code without specs. The forward pipeline does not help — you cannot ideate something that already shipped years ago. Adjacent open seeds tell us this gap is felt: `cross-repo-source-idea-references-should-be-supported-by-lin` (multi-repo source pointers) and `idea-skills-should-pick-destination-repo-not-default-to-cwd` (destination resolution) both anticipate scenarios this skill creates. We need a parallel skill that runs backward: from code to Features.

This Idea was originally drafted as a single monolithic skill covering scan → research → synthesis → derivation. A pre-approval review pass (see Review Notes) surfaced a stronger shape: **split off the cheap scan phase as a separate skill `specstudio:survey`**, leaving `specstudio:retrofit` as the opt-in deep path that consumes `survey`'s output. Subsequently the user identified that the feedback loop the Test Engineer review called for needs its own home — a third sibling, `specstudio:retrofit-evaluation`, that scores retrofit output against ground-truth specs and closes a self-improvement cycle on the retrofit prompts and architecture.

The family is therefore three sibling Ideas:
1. **`survey-skill`** — cheap, fast skeleton scan + research-zone proposal. Activation hook; standalone value.
2. **`retrofit-skill`** — this Idea. Opt-in deep path that consumes a survey artifact and produces lint-clean Feature artifacts.
3. **`retrofit-evaluation-skill`** — internal-facing skill that diffs retrofit output against ground-truth specs (using retrofit's `--ignore-existing-specs --output-dir` calibration mode), produces a quality score, and feeds into the self-improvement loop for retrofit prompts and architecture.

## Recommended Direction

Add a new specstudio skill — `specstudio:retrofit` — that **consumes a survey artifact produced by the sibling `specstudio:survey` skill** (architecture summary + research-zone proposal + structural-manifest inventory) and turns it into lint-clean Feature artifacts under `spec/features/<slug>/`. Retrofit is the opt-in deep path; users get value from `survey` alone (2-minute runtime, no gates, shareable architecture summary) and only run `retrofit` if they want Features. The skill uses a **two-tier agent architecture** with explicit phase gates.

**Agent roles:**

- **`retrofit-coordinator`** (one per run) — accepts a survey artifact as input (the skeleton scan is delegated entirely to `specstudio:survey`), runs the Phase 1 source-reading consent gate, dispatches researchers in parallel against the zones the survey proposed, merges and dedupes their structured outputs, presents the candidate Feature list to the user, and drafts the approved Feature artifacts. It is the user-facing agent.
- **`retrofit-researcher`** (N per run, parallel) — assigned a *research zone* (a directory cluster). Reads source, tests, and docs inside the zone. Receives a **read-only shared brief** from the coordinator (architecture summary inherited from the upstream survey artifact, detected-frameworks glossary, cross-cutting-concern registry built up so far) so researchers use shared vocabulary and the coordinator can dedupe deterministically downstream.

**Researcher emits output via structured tool calls, one Feature candidate at a time** — not a monolithic bundle. Each Feature is submitted via a `submit_feature_candidate(...)` tool call whose arguments conform to `feature-candidate-schema-v1`; the harness **validates against the schema at the API boundary**, and on validation failure the researcher receives the error and retries just that Feature (max 2 retries before falling back to "drop this candidate, surface as warning to coordinator"). This pattern gives JSON's emit reliability via native tool-call APIs while making failures isolate to single Features rather than corrupting the whole bundle. After all Feature submissions, the researcher submits a `submit_zone_summary(...)` tool call carrying `cross_cutting_observations`, `test_inventory`, `test_gaps`, and the list of emitted Feature slugs.

**On-disk shape** (transient, hidden, `.gitignore`'d by default): the harness writes each validated tool-call argument to `.retrofit-research/<run-id>/zones/<zone-slug>/<feature-slug>.yaml` (YAML for human readability when inspecting failed runs). The `zone_summary` lands at `.retrofit-research/<run-id>/zones/<zone-slug>/_summary.yaml`. Successful runs clean these up at exit; failed runs preserve them for debug. A `--keep-research-artifacts` flag preserves them on success too.

**Per-Feature schema fields** (conforming bundle): `working_title`, `one_liner`, `source_pointers` (file:line ranges), `observed_behaviors` (terse summary lines), `test_presence` (which tests cover this Feature), `ac_seeds` (short seed lines — full Given/When/Then ACs are drafted at Phase 4, not in the seed), `proposed_parent` (slug or null), `proposed_children` (list of slugs), `test_gaps` (per-Feature edge cases / missing-test observations with `description`, `suspected_edge_case_type`, `severity`). The `proposed_parent` and `proposed_children` fields capture **Feature hierarchy** — SpecScore Features are organized as parent/child via `spec/features/<parent>/<child>/` on disk, and used for composition / inheritance (a child Feature inherits its parent's context and constrains it).

**Soft cap**, not hard cap, on Feature count per researcher: **50 Features** — when exceeded, the researcher emits a `zone_too_large: true` signal in the zone summary suggesting the coordinator split the zone. Not a refuse, because per-Feature emit isolation means a large zone is annoying but not catastrophic.

Researchers do not see each other's outputs and do not write artifacts outside their own `.retrofit-research/<run-id>/zones/<zone-slug>/` directory.

**Phases** (retrofit's own; the skeleton scan + research plan is delivered by `specstudio:survey` upstream and is **not** a retrofit phase):

- **Phase 1 — Survey ingestion & source-reading consent gate** (coordinator, before any source reads). Loads the survey artifact produced by `specstudio:survey`. Re-validates the survey is current (compares the `HEAD` SHA and `git status --porcelain` digest the survey captured against the current working tree; if drift exceeds a threshold or staleness exceeds a TTL, re-invoke `survey` rather than guess). **Ownership split with `survey-skill`:** `survey` produces a *filename-based* sensitive-path inventory (hints only — `.env*`, `secrets/**`, `*.pem`, `*.key`, `**/fixtures/**`, suspected lockfile-mismatch entries, `git-crypt` / submodule / LFS pointers). Retrofit's Phase 1 then runs the *actual* content-scanning secret scanner (gitleaks / trufflehog / equivalent) against the zones the survey proposed, seeded by the survey's inventory hints. This division is deliberate: filename heuristics are cheap and fit survey's no-source-reads constraint; content scanning requires reading file bytes and belongs in retrofit's security gate. Phase 1 presents the user with a consolidated consent screen listing zones, file counts per zone, both heuristic hits (from survey) and content-scanner hits (from this phase), and the multi-repo set with each repo's trust level. The skill **refuses to proceed** on scanner hits without an explicit per-finding override. This gate exists because the user-approval gate in Phase 3 is on Feature *output*, not on data ingress — too late for regulated codebases (HIPAA, PCI, export-controlled).
- **Phase 2 — Parallel deep research** (N × researcher). Each researcher works its assigned zone (zones come from the survey) and returns the structured bundle above. No coordination between researchers; the shared brief flows one-way from coordinator → researcher.
- **Phase 3 — Synthesis & user approval gate** (coordinator). Merges and dedupes the researcher bundles (cross-cutting concerns like auth/logging that surface in multiple zones get folded). **Resolves Feature hierarchy** — reconciles `proposed_parent` / `proposed_children` hints from researchers into a single coherent parent/child tree, breaking ties using directory structure as a tiebreaker. Presents the consolidated candidate Feature **tree** (not flat list) — working title, one-liner, source pointers, and proposed position in the hierarchy — to the user. **The user MUST approve, reject, or edit the tree before any drafting starts** — including reparenting Features, promoting children to parents, collapsing siblings into one, or splitting a Feature into parent + children. This gate exists explicitly so researchers cannot drift the run into Features the user did not want. **Bulk-operations UX is in-scope for MVP** (escalated from Open Question by the re-review): the gate UI provides bulk-accept, sort-by-test-coverage, "draft the top N" shortcut, per-Feature inline edit, and tree manipulation (move, promote, demote, collapse). Line-by-line approval of 100+ candidates is a known quit moment; the gate must scale or be removed as a gate. **Bulk-accept excludes `classification: speculative` ACs by default** — speculative ACs always require individual review because they're explicitly *proposed* behaviors with no test backing. A user can opt to bulk-include speculative ACs (advanced flag), but the default refuses; otherwise the speculative-AC discipline collapses into "ship hallucinations behind a label."
- **Phase 4 — Feature derivation & staging** (coordinator, may re-dispatch researchers for gaps). For each approved Feature, draft a lint-clean artifact under `spec/features/<slug>/` (or the `--output-dir` sandbox in calibration mode) with title, behavior, Given/When/Then ACs derived from tests and observable interfaces, and source-of-truth pointers. Each AC carries a **two-axis provenance trailer**: `derived-from: [<source-set>]` (a set, not an enum — values: `test`, `interface`, `type`, `schema`, `doc`, `inferred`; an AC may carry multiple) AND `classification: <one of: asserted-intent | current-behavior-lock-in | speculative>`. The first axis says *what evidence supports the AC*; the second says *whether we trust that evidence as intent*. Critical because `derived-from: test` on a passing test asserting `divide(10,0) === Infinity` is accurate provenance but locks in a bug — `classification: current-behavior-lock-in` flags that explicitly. `asserted-intent` is reserved for ACs where multiple independent sources (e.g. `test + doc + interface`) agree; `speculative` for `derived-from: [inferred]` only. **Status defaults uniformly to `Implementing`**; `Stable` requires an explicit human gate per Feature regardless of test coverage signal (asymmetric cost — a false-`Stable` retrofitted Feature becomes canonical spec and future devs "fix" code to match it). Before staging, each draft passes an **output-side DLP scrub** (secret patterns, internal hostnames/IPs, customer identifiers from fixtures, security-relevant TODOs) — the `specscore lint` step validates structure, not content sensitivity, so this is its own pass. DLP effectiveness is graded by `retrofit-evaluation-skill` against a planted-secrets corpus (recall and precision both reported); the scrub is not security theater if-and-only-if eval covers it. Each artifact is linted and staged. Index updated. Skill exits — no commit.

**Tooling stance:** retrofit itself adds no new CLI surface in MVP. The skeleton-scan tooling decisions (`git ls-files` and manifest reads vs. a `specscore` helper command) move with the upstream scan into the `survey-skill` Idea. Retrofit relies on whatever survey produces. For Phase 1's secret scan, retrofit dispatches an external scanner (gitleaks / trufflehog / equivalent) as a subprocess — no scanner is built in-house; if no scanner is available locally, the skill prompts the user to install one before continuing.

**Multi-repo mode** branches at the very start of Phase 1 via a single wizard question; the skill writes Features under the cwd "spec home" and emits cross-repo source pointers for code in sibling repos. Multi-repo mode declares the `cross-repo-source-idea-references-should-be-supported-by-lin` seed as a hard dependency rather than smuggling it in.

Branch convention: in both modes the skill **defaults to** a branch named `specscore/<slug>` on every participating repo, where `<slug>` is the Idea or Feature slug the retrofit run is scoped to. In multi-repo mode this same branch name is used uniformly across every sibling repo so the retrofit work is correlated by branch name alone — no separate manifest needed. The convention is a **default, not a gate** — real multi-repo teams have protected-branch rules and CI prefixes, and refusing to operate without `specscore/<slug>` would make retrofit a git-workflow change rather than a spec tool. Override path: user may specify an alternate branch name via flag, applied uniformly across the set. The skill still refuses to write Feature artifacts on `main` / `master` (hard rule), and warns — but does not refuse — when sibling repos can't all checkout the same branch name (dirty trees, divergent local branches), letting the user resolve before continuing. Multi-repo mode additionally records a **per-repo trust level** at Phase 1 (e.g. spec-home repo = high-trust, sibling vendor mirror = low-trust); summaries from lower-trust repos never cross-fertilize Features written into higher-trust repos. Branch-name correlation is fundamentally vulnerable to confused-deputy (anyone with write access to a sibling repo can plant a `specscore/<slug>` branch); see Open Questions for the provenance-signing mitigation.

**Tests are the primary source for Requirements and ACs.** Researcher prompts explicitly instruct: when a behavior is covered by a test, the AC mirrors the test's assertion and carries `derived-from: [test]` provenance. Tests are the highest-fidelity available signal of intended behavior because they encode executable expectations the team committed to; documentation can lie, code can drift, but tests fail loudly when wrong. Each AC carries a back-reference to the specific test(s) it derives from (file:line or test name); reviewers can navigate from spec to test directly. When no test covers a behavior but the code expresses it (an exported function, a route handler, a schema constraint), the AC carries `derived-from: [interface]` and `classification: current-behavior-lock-in` — flagging that the spec captures what the code does, not necessarily what it should do. Researchers explicitly enumerate test styles found in the zone (unit / integration / e2e / snapshot / property-based) and translate accordingly: property-based tests express invariants and produce strong universal-quantifier ACs; snapshot tests produce no behavioral ACs (they assert "looks like last time," which is not intent); mocked-heavy unit tests assert collaborator calls, which are implementation-detail ACs and should be marked as such. The researcher's structured output bundle includes a per-zone `test_inventory` capturing this taxonomy so the coordinator can present test-coverage signal in the Phase 3 approval gate.

**Hierarchy-conflict precedence.** When researcher hints contradict — e.g. researcher A (zone `api/`) proposes Feature X as parent of Y, but researcher B (zone `auth/`) proposes Y as a sibling of X — the coordinator resolves with this precedence (highest wins): (1) **cross-cutting concerns beat directory structure** — auth/logging/metrics are typically parent Features even when their implementations span directories, so a cross-cutting hint from any researcher overrides directory-based sibling proposals; (2) **deeper directory nesting beats shallower** when neither side is cross-cutting; (3) **majority-vote** when researchers propose the same depth — N researchers proposing X-as-parent-of-Y beats one researcher proposing Y-as-parent-of-X; (4) **alphabetical slug as a tiebreaker of last resort** for deterministic output. Conflicts that hit (4) are surfaced as warnings in Phase 3 so the user can override.

**Researchers do not treat tests as exhaustive.** Existing tests cover *some* behaviors; they almost never cover all. Researchers are explicitly instructed to identify **missing use cases and edge cases** — behaviors visible from the code, interfaces, or domain reasoning that lack test coverage. These surface as a per-Feature `test_gaps` field in the researcher bundle: `[{ description, suspected_edge_case_type, severity }]`. Edge-case categories the researcher explicitly looks for: error and exception paths, boundary conditions (empty input, max input, off-by-one), concurrent or race-condition behavior, security-sensitive paths (auth bypass, injection, IDOR), failure-mode behaviors (network errors, partial writes, timeouts), accessibility and i18n paths, and resource-exhaustion behavior. For each gap, Phase 4 produces an AC marked `derived-from: [interface]` (or `[inferred]` if no interface evidence either) with `classification: speculative` — explicitly flagging it as a *proposed* AC the team should validate, not asserted current behavior. The Phase 3 approval gate surfaces gap-ACs distinctly from test-backed ACs so the user can accept, reject, or edit them individually. This converts retrofit from "spec what tests prove" to "spec what tests prove PLUS what the spec ought to cover" — closer to what a thoughtful engineer would write by hand.

**Feature hierarchy is first-class.** SpecScore Features are not a flat list — they form a tree on disk (`spec/features/<parent>/<child>/`) and are used for composition and inheritance: a child Feature inherits its parent's context and constrains a narrower behavior. Retrofitted Features must reflect the natural hierarchy of the codebase rather than flattening everything to siblings. The coordinator emits a parent/child tree at Phase 3 (not a list); Phase 4 writes child Features into nested directories matching the approved tree. Cross-cutting concerns (auth, logging) are typically *parent* Features with children per consumer.

**Idempotency stance.** MVP retrofit runs are **non-idempotent** — re-running retrofit against the same repo produces a fresh sandbox of Feature artifacts; it does not diff or merge against the existing `spec/features/` tree. Two reasons: (1) reconciliation is hard and shipping it inside the MVP timeline would compromise the core derivation work; (2) the calibration-mode workflow (`--ignore-existing-specs`) requires a non-reconciling baseline anyway. Incremental / re-run-with-merge behavior lands post-MVP via the Open Question on re-run semantics — until then, retrofit's documented expectation is "use against an empty `spec/features/` tree, or a `--output-dir` sandbox."

Naming: `retrofit` fits the single-verb house style (ideate, specify, plan, implement, verify, recap) and is the term engineers reach for when describing 'applying specs to a thing that already exists.'

## Alternatives Considered

- **Name it `specstudio:derive`.** Accurate but feels formal/academic; "derive" implies a deductive process, which oversells the fidelity we can actually deliver from code → spec. Loses on warmth and product clarity.
- **Name it `specstudio:backfill`.** Also clear, but evokes database backfills more than spec work; engineers' first mental image is "filling a missing column," not "writing specs for existing code." Close second choice.
- **One-shot mega-skill that also writes Ideas + Plans retroactively.** Rejected. Retroactive Ideas are an oxymoron (the idea was had, lost, and shipped years ago). Plans describe forward work; retro Plans are noise. The user explicitly scoped this to Features-only.
- **Out-of-band tooling (CLI command, no skill).** Possible but loses the conversational refinement loop that makes the candidate-Feature list trustworthy. Code → spec needs human-in-the-loop iteration; the *skill* is where the value lives. The CLI may grow helpers (e.g., `specscore retrofit scan`), but the user-facing artifact is the skill.
- **Multi-repo via a top-level manifest file.** Considered and rejected in favor of the uniform `specscore/<slug>` branch convention. A manifest would be a new artifact type to maintain; branch-name correlation reuses git as the source of truth and degrades gracefully (a missing branch is a missing repo, no extra state to drift).
- **Single-tier agent (one big retrofitter does everything).** Rejected. Real repos have enough surface area that one agent's context window becomes the bottleneck, and synthesis quality degrades. The two-tier coordinator+researcher split matches how a tech lead actually does this work — skim the architecture, slice into zones, hand off, integrate — and isolates each researcher's context to its zone.
- **Slice researchers by Feature instead of by directory cluster.** Rejected — researchers would overlap on cross-cutting concerns (auth, logging, middleware), and the slicing depends on knowing the Features beforehand, which is what we're trying to discover. Directory-cluster slicing plus a coordinator dedup pass is more honest.
- **`specscore retrofit scan` CLI command on day one.** Rejected for MVP. We do not yet know what stable output shape the coordinator wants; building the CLI first is speculative flexibility. `git ls-files` plus manifest reads cover MVP cleanly. Revisit after the skill ships and the scan output shape stabilizes — if it graduates, it belongs in `specscore`, alongside `specscore code` and `specscore feature`.
- **"1–3 equal research-plan options" presented to the user.** Rejected — a senior engineer picks one and explains why, rather than handing the user three equal-weight choices. The coordinator presents **one recommended plan with up to 2 alternatives noted**, matching the cadence `ideate` uses.
- **Monolithic skill covering scan + research + synthesis + derivation in one run** (this Idea's original shape). Rejected after the pre-approval Developer Advocate review surfaced that the activation moment landed in Phase 4 — users invested through three phases before seeing any value, and abandonment risk was high. Accepted alternative: split off the upstream skeleton scan as a separate `specstudio:survey` skill (~2-minute runtime, no gates, shareable architecture summary as a standalone artifact). This Idea now describes only the retrofit-skill half; the sibling `survey-skill` Idea is referenced as a hard dependency. Survey is the activation hook; retrofit is the opt-in deep path.

## MVP Scope

A **four-week spike**: ship `specstudio:retrofit` end-to-end for a single-repo, JavaScript/TypeScript or Python project, with two depth modes (`shallow` = docs+routes+exports, `deep` = full code+tests). Depends on `survey-skill` shipping its MVP first (or in parallel). Multi-repo lands as a wizard branch that asks the question but defers to single-repo flow until the cross-repo lint dependency is resolved. Week 1 absorbs the 6+ Must-be-true assumption spikes (schema-conformance, shared-brief vocabulary, AC-provenance accuracy, secret-scan coverage, injection-fencing, dedup correctness); weeks 2–3 build the coordinator + researcher prompts + Phases 1/2/3/4; week 4 hardens against the calibration corpus.

**Calibration mode** (in-MVP, required for the success criterion). The skill accepts two flags that work together:
- `--ignore-existing-specs` — instructs the run to ignore any `spec/` tree already present in the target project. **Propagates upstream to `survey-skill`**: when retrofit runs in calibration mode, it re-invokes `survey` with the same flag so the survey artifact is *also* generated without spec-vocabulary leakage. Without this propagation the survey's architecture summary would encode ground-truth labels and the shared brief would smuggle them into researchers — a context-window leak that would silently inflate calibration scores. Researchers under this flag do not read existing Features, Plans, or Ideas under any circumstance. Default is off (normal retrofit can and should reconcile with existing specs).
- `--output-dir <path>` — writes Feature artifacts and a sandboxed index (`<path>/README.md`) under the given path instead of `spec/features/`. The real `spec/features/README.md` is **not** touched in calibration mode; the sandbox is fully self-contained for the diff against ground truth. Default writes to `spec/features/` and updates the canonical index.

Together these enable a controlled comparison: retrofit a project that already has hand-written SpecScore specs into a sandbox output, then diff against the real `spec/features/` tree as ground truth. This is the primary validation mechanism for the AC-inference and Status-default assumptions, and it converts the success criterion into something falsifiable. The diff-and-grade tooling itself lives in `retrofit-evaluation-skill`.

**Success criterion** (sharpened, using calibration mode): retrofit `specstudio-skills` AND at least one ugly legacy repo the maintainer did **not** write (dogfooding `specstudio-skills` alone biases toward small, well-tested, TypeScript-shaped codebases). For `specstudio-skills`, run with `--ignore-existing-specs --output-dir /tmp/retrofit-out` and verify: ≥80% of produced Features pass `specscore lint` first try; **Coverage precision ≥0.7 AND Coverage recall ≥0.7** (bipartite matching per `retrofit-evaluation-skill`'s algorithm); **AC faithfulness Cohen's κ ≥0.6** (or inter-human ceiling, whichever is lower) against ground-truth ACs. Metrics align with `retrofit-evaluation-skill` — there is exactly one definition of these bars, owned by eval, referenced here.

**Sequencing honesty.** The quantitative success bars above (≥80% lint, ≥70% match, ≥70% AC faithfulness) cannot be enforced by retrofit alone — they require the sibling `retrofit-evaluation-skill` to land. Retrofit MVP therefore ships in two stages: **stage A (week 4)** — retrofit produces output and passes a manual qualitative review on the calibration corpus; **stage B (gated on retrofit-evaluation MVP, ~week 7)** — the quantitative bars are measured automatically and become the actual ship gate. The 9-week serial chain (`survey` 2wk → `retrofit` 4wk → `retrofit-evaluation` 3wk) is the honest end-to-end timeline for the closed loop; this Idea is explicit about that rather than pretending retrofit can validate itself.

**Family-level success criterion** (load-bearing, owned by this Idea since retrofit sits in the middle of the family): *a user can run `specstudio:survey` and `specstudio:retrofit` against an ugly legacy repo the user did not write, and the produced Feature artifacts pass the success bars above on at least 2 such repos.* This goal is what the three sibling Ideas (`survey-skill`, `retrofit-skill`, `retrofit-evaluation-skill`) exist to deliver collectively. Each sibling has its own narrower success bar; none of them on their own answers the family question. The cross-family review surfaced that this goal was previously homeless across the three Ideas; it now lives here.

## Not Doing (and Why)

- Retroactive Idea generation — retroactive Ideas have no decision-making value; the trade-offs were already made and shipped.
- Retroactive Plan generation — Plans describe forward work; retro Plans are dead weight.
- Auto-promotion to `Status: Stable` — under any signal. The retrofit skill never auto-assigns `Stable`; default is uniformly `Implementing`. `Stable` requires explicit per-Feature human decision. False-`Stable` is asymmetrically costly (becomes canonical spec; future devs "fix" code to match it; silent regressions ship), and the consultant audience has no authority to declare anyone else's code Stable in the first place.
- Running researchers without pre-dispatch consent — Phase 1's data-ingress gate is non-optional. The Idea will not propose a flow that reads source under user-approval-by-output-only semantics.
- Cross-repo lint support — tracked by existing seed cross-repo-source-idea-references-should-be-supported-by-lin; declared as a dependency, not in scope.
- Language-agnostic v1 — pick 1-2 languages we can do well; expand by demand.
- Automated git history mining — useful but expensive and easy to over-fit; defer past MVP.
- `specscore retrofit scan` CLI command in MVP — defer until the skill demonstrates a stable scan-output shape; premature CLI surface is harder to remove than to add.
- Reading source files during the upstream skeleton scan — that scan (delegated to `survey-skill`) is restricted to file tree plus an allowlist of structural manifests; source reading is exclusively the researchers' job in Phase 2.

## Key Assumptions to Validate

| Tier | Assumption | How to validate |
|------|------------|-----------------|
| Must-be-true | Users will accept a "scan → propose Feature list → user edits → derive" loop as worth their time vs. writing specs by hand | Run MVP on this repo plus 2 external repos; ask 3 users whether the loop saved time vs. the from-scratch alternative |
| Must-be-true | Subagent dispatch can produce a Feature draft of acceptable quality from a bounded code slice (one subsystem) | Spike one Feature end-to-end manually with a Plan-style subagent prompt before locking the design |
| Must-be-true | Researchers can reliably return the strict structured output bundle (`feature_candidates` + `cross_cutting_observations`) so the coordinator can do a deterministic merge, not a prose interpretation. Realistic LLM JSON malform rate is 5–15%; with N=10 researchers a per-run failure is near-certain without retries. Design must include schema validation on receipt, bounded repair retries (proposal: max 2), and a researcher-hard-failed → re-dispatch path | Spike N=3 researchers in parallel; measure schema-conformance rate; verify retry/repair loop converges without runaway cost |
| Must-be-true | Researchers honor the shared read-only brief and produce summaries with consistent vocabulary — i.e. they don't independently invent divergent names for the same framework or pattern | Spike N=3 researchers on adjacent zones of the same repo; verify the framework glossary and cross-cutting registry are referenced verbatim in outputs |
| Must-be-true | AC inference from tests can carry useful provenance (`derived-from: test|interface|inferred`) without fabricating intent. Tests encode *implementation including bugs*; the provenance trailer lets reviewers tell asserted intent from current-behavior lock-in | Pilot on 5 Features from this repo; have a human grade whether provenance trailers accurately classify each AC; require ≥90% agreement on `test`-tagged ACs (bar is high because false provenance defeats the purpose) |
| Must-be-true | Pre-dispatch secret scan (Phase 1) catches the realistic secret-density of structural manifests (`docker-compose.yml`, `package.json` scripts, IaC) plus test fixtures; the manifest allowlist is empirically *higher* secret-density than average source, not lower | Run gitleaks/trufflehog against 3 real repos including this one; verify the scanner catches what a human reviewer would catch; measure false-negative rate |
| Must-be-true | Instruction-vs-data fencing in researcher prompts is sufficient to resist prompt injection from repo content (comments, fixtures, READMEs, sample JSON, vendored OSS) | Pilot with an adversarial seed: plant a prompt-injection string in a test fixture and a README; verify the researcher returns conformant output without obeying the injection |
| Must-be-true | Directory-cluster slicing plus a coordinator dedup pass actually catches cross-cutting concerns (auth, logging, middleware) rather than missing them | Pilot on a repo with a known cross-cutting concern; verify the coordinator surfaces it as a single Feature, not duplicates or omissions |
| Must-be-true | The upstream `survey-skill` output (architecture summary + zone proposal) is sufficient input for retrofit's coordinator to dispatch researchers without re-reading the file tree | Once survey-skill MVP exists, run retrofit Phase 1 against three real survey artifacts; verify retrofit needs no additional pre-research scanning |
| Must-be-true | The uniform `specscore/<slug>` branch convention is acceptable to teams (i.e. they are willing to create that branch across every participating repo) | Validate with 2 multi-repo teams during MVP discovery; if rejected, fall back to a manifest |
| Should-be-true | Scan-phase signals (file counts, languages, framework markers, test density) are enough to estimate depth-mode cost within ±50% | Calibrate the estimator against 3 representative repos; measure actual vs predicted token spend per depth mode |
| Should-be-true | The cross-repo lint gap is the *only* blocker for multi-repo mode | Walk a multi-repo scenario manually end-to-end and list every lint/CLI gap encountered |
| Should-be-true | `Status: Stable` vs `Status: Implementing` can be decided automatically from test coverage signals without false positives | Pilot on 5 retrofitted Features; have a human grade the assignments; require ≥80% agreement |
| Might-be-true | A single skill is the right shape vs. splitting `retrofit-scan` and `retrofit-derive` into separate skills | Defer; revisit after MVP based on actual checkpoint friction |
| Might-be-true | Two depth modes are enough; three or more would be over-engineering | Defer until usage data exists |


## SpecScore Integration

- **New Features this would create:** `retrofit-skill` (one parent Feature, likely subdivided at spec time into `skeleton-scan-and-research-plan`, `parallel-research`, `synthesis-and-approval-gate`, and `feature-derivation-and-staging` matching the four-phase architecture).
- **Existing Features affected:** None directly — this is additive. May share a reviewer prompt with `specify` for AC quality (both produce Feature ACs from natural-language input).
- **Dependencies:**
  - Sibling Idea `survey-skill` — **hard dependency**. The upstream skeleton scan (file-tree + structural-manifest inventory + research-zone proposal) is delivered by `specstudio:survey`. Retrofit consumes survey's output and does not duplicate it. The contract between survey and retrofit is a **named schema** (working title: `survey-output-schema-v1`) owned jointly: survey produces it, retrofit validates on ingestion. The schema is in-scope at spec time for whichever Idea ships first.
  - Sibling Idea `retrofit-evaluation-skill` — **soft dependency**. Retrofit ships its calibration mode (`--ignore-existing-specs --output-dir`) independently, but the self-improvement loop on retrofit prompts and architecture closes only when evaluation can score the output. Retrofit MVP can ship with manual evaluation; the loop becomes automated when retrofit-evaluation ships.
  - Seed `cross-repo-source-idea-references-should-be-supported-by-lin` — **blocking for multi-repo mode**. Until the lint allows cross-repo source pointers, multi-repo mode can only ship the branch-coordination scaffolding, not actual cross-repo Feature artifacts.
  - Seed `idea-skills-should-pick-destination-repo-not-default-to-cwd` — informs the cwd / spec-home resolution behavior in multi-repo mode.
  - Existing `specscore` CLI `feature` and `lint` commands — the skill is a thin orchestrator over them; no new CLI verbs required for MVP.
  - External secret scanner (gitleaks, trufflehog, or equivalent) — required at Phase 1; not built in-house. Skill prompts to install if absent.

## Open Questions

**Decided since first draft:** `specstudio:survey` split (yes, sibling Idea drafted); MVP timeline (4 weeks, no cuts; 9-week chain for full closed loop); `Status:` default (uniformly `Implementing`, `Stable` requires human gate per Feature); agent names (`retrofit-coordinator` / `retrofit-researcher`); plan presentation (1 recommended + 2 alternatives); shell-tools-first (decision moves with survey-skill); calibration mode propagates `--ignore-existing-specs` to upstream survey; `--output-dir` writes a sandboxed index; phases renumbered (1/2/3/4); provenance trailer is two-axis (`derived-from: [<set>]` + `classification:`); tests are the primary AC source; Features are hierarchical (parent/child reflected in disk layout and Phase 3 approval gate); Phase 3 bulk-ops UX is in-scope for MVP; sensitive-path inventory ownership split (survey produces hints, retrofit runs content scanner); idempotency is non-idempotent in MVP (fresh sandbox per run); family-level success criterion is owned by this Idea; **researcher output is one-Feature-per-tool-call with schema enforcement at the API boundary, serialized as YAML on disk under `.retrofit-research/<run-id>/zones/<zone-slug>/<feature-slug>.yaml` (transient, hidden, `.gitignore`'d)**; consultant audience handled implicitly by the existing `Stable`-gate requirement (no separate audience flag in MVP).

**Open:**

- Value for retrofitted Features' `**Source Ideas:**` line: proposal is a literal sentinel (e.g. `Retrofitted` or `—`). May require a `specscore` lint adjustment.
- Subagent parallelism in Phase 2: cap at N=? Dispatch all zones at once or batch by depth/risk? Probably batch — defer to plan time, but the dedup cost grows quadratically with N so a hard ceiling is wise.
- Multi-repo sibling-repo discovery: explicit user list, a manifest, sibling directories on disk, or remote-org enumeration? MVP probably says "user lists them"; future could enrich.
- Interaction with `specscore.yaml`: does a retrofit run write a config entry recording the retrofitted set so subsequent runs are idempotent / incremental? Lean yes, defer details.
- Should the skill emit a event (`feature.retrofitted`) distinct from `feature.drafted` so downstream tooling can treat retrofitted Features differently?
- Dedup mechanics — concrete merge rules: file-path overlap ratio threshold? AST symbol overlap? Embedding similarity? Working titles will collide on common verbs ("validation", "auth middleware") and divergent descriptions of the same thing will false-split. Deserves its own spec-time treatment.
- Shared researcher brief — what exactly does it contain, and how is it kept under a context-size budget across N researchers? Likely: architecture summary digest (from survey), detected-frameworks glossary, cross-cutting-concern registry built up across researchers (which means researchers can't all be truly parallel — there's a serial phase or eventual-consistency tradeoff).
- AC provenance trailer — exact format, and how it interacts with `specscore` lint. Lint rule extension?
- Three-audiences divergence — does the consultant audience need a separate `Status:` policy (they have no authority to declare anyone else's code anything)? Or a separate output mode entirely (a "learning artifact" survey, not a Feature)?
- 500k-LOC scaling — how do zones get sub-divided when a researcher's zone exceeds context budget? Hierarchical clustering? Hard cap with split rule?
- `git-crypt`, submodules, LFS pointer handling — refuse, warn, or skip silently? Each has different security implications; needs a deliberate policy.
- Re-run / idempotency semantics — what happens on retrofit run #2 against the same repo? Does Phase 3 diff against existing `spec/features/`? Does it propose only deltas?
- Branch-provenance check in multi-repo mode — signed commits, merge-base validation against `main`, or accept the confused-deputy risk? The threat is real but the mitigation may be heavy for MVP.
- Calibration mode: diff-and-grade tooling lives in the sibling `retrofit-evaluation-skill` Idea — retrofit itself only produces the output to be evaluated. For retrofit MVP, evaluation is manual review against the rubric in the success criterion; the automated loop activates when `retrofit-evaluation` ships.
- Calibration mode: should `--ignore-existing-specs` also hide `spec/research/` and any non-canonical SpecScore directories, or strictly the canonical tree?
- Bulk-operations UX on the Phase 3 approval gate — at 200 candidate Features, line-by-line review is a quit moment. Need bulk-accept, confidence-ranked sorting, or a "draft the top N by test coverage" shortcut.
- Funnel telemetry — do we emit phase-boundary events so we can learn where users abandon (Phase 1 → 2 → 3 → 4 dropoff curve)? Useful for post-MVP iteration, sensitive for privacy. Defer.
- **Scope-expansion candidates: code review, security report, improvement plan.** Researchers already deeply read and reason about every line in their zone — the expensive token spend is sunk. Producing additional artifacts from the same research pass is marginal cost. User surfaced this directly: "should we also provide code review, improvement plan, security report?" Three design options, none committed:
  - **(A) Sibling skills consuming the same researcher bundle.** Add 3 new sibling Ideas (`code-review-skill`, `security-audit-skill`, `improvement-plan-skill`) that share retrofit's researcher pass — extending the researcher output bundle with `code_quality_observations`, `security_observations`, `improvement_opportunities` fields. Sibling skills then synthesize their respective artifacts. User opts in via CLI flag (`--also-produce: code-review,security,improvement-plan`) at the start of the run, or via an end-of-Phase-3 prompt ("research is done; produce additional artifacts?"). Most architecturally clean — keeps retrofit focused on Features.
  - **(B) Single sibling "retrofit-insights" skill.** Bundles all three artifact types into one downstream skill that reads retrofit's research bundle and produces a single combined report (or per-artifact subsections). Lower architectural overhead than (A), but loses the ability for users to opt in to one without the others, and conflates three quite different output disciplines.
  - **(C) Fold into retrofit itself.** Reject. Code review, security audit, and improvement plans are each their own discipline (semgrep, ESLint, tfsec, etc. are dedicated tools for good reasons); folding them into retrofit makes it a worse Feature-spec tool AND a worse code-review tool. Skill scope discipline ("say no to 1,000 things") strongly argues against.
  - **Recommendation:** (A). Defer the sibling-Idea drafting until retrofit MVP ships and the researcher bundle has proven stable — premature scope expansion would block retrofit on three new quality bars. Once retrofit ships, add `--also-produce` as an opt-in hook; users choose which extra artifacts to spawn. The researcher's structured bundle MUST be designed at spec time with these extension fields in mind, even if they remain empty in MVP.
- Post-MVP: does any part of the skeleton scan graduate into a `specscore` helper command? *(Moves with the scan to the `survey-skill` Idea.)*

## Review Notes

This Idea was subjected to a pre-approval review pass on 2026-05-22 by a 5-role agent panel dispatched in parallel. Substantive findings have been folded into the sections above; this section preserves the audit trail so future readers can see what shaped the design.

- **Backend Architect** — researcher output schema is load-bearing but under-specified (5–15% LLM JSON malform rate at N=10 = near-guaranteed per-run failure); dedup/merge gets one sentence for the hardest problem; researchers need a shared read-only brief or vocabulary drifts and breaks downstream merge; Phase 4 may collapse into Phase 2 with "researcher mode = draft"; 500k-LOC scaling breaks the cost model without hierarchical clustering; test-to-feature mapping crosses zone boundaries; idempotency / re-run semantics unspecified.
- **Test Engineer** — "AC inference from tests" conflates test code with intent (passing test on `divide(10,0)===Infinity` locks in the bug); "test-backed" had three plausible definitions with wildly different failure modes; defaulting `Status: Stable` on weak signal is the worst-case false-confidence failure; per-AC provenance trailer needed to distinguish asserted intent from current-behavior lock-in; snapshot tests yield no behavioral ACs; property-based tests need a slot in the schema; no Phase 4 approval gate on derived ACs.
- **Security Auditor** — heaviest single review and the most actionable. Researchers ingest secrets and PII as routine input; prompt-injection surface is the entire codebase; structural-manifest allowlist is empirically *higher* secret-density than average source; multi-repo collapses trust boundaries; no user gate before researchers read source; output channel has no DLP; `git ls-files` reveals `git-crypt` / submodule / LFS pointers; branch-name correlation enables confused-deputy. Drove Phase 1 introduction and the per-repo trust-level requirement.
- **Sprint Prioritizer** — 2-week MVP dishonest given 6+ embedded validation spikes; recommended cuts in order (multi-repo wizard → second depth mode → cost estimator → parallel N>1) if timeline can't move; success criterion non-falsifiable; called out three Open Questions as actually blocking (researcher schema, `Source Ideas:` sentinel, Status default rule). Drove the 4-week re-scope and the falsifiable success criterion.
- **Developer Advocate** — no one-sentence pitch; activation moment lands in Phase 4, too late; Phase 3 gate is friction at 200-feature scale (need bulk-accept + ranking); three-audiences-one-workflow is hand-wave (consultant has no authority to declare `Stable`); uniform branch convention should be default, not gate; dogfooding `specstudio-skills` biases toward easy targets. **Strategic suggestion that drove the biggest design change: split into `specstudio:survey` (the upstream skeleton scan standalone, activation hook) + `specstudio:retrofit` (opt-in deep path).**

The five reviewers converged independently on four findings, which are now load-bearing in the design: (1) MVP timeline was dishonest at 2 weeks, (2) `Status: Stable` default was asymmetrically dangerous, (3) the researcher structured-output schema needed retry/validation policy, (4) dedup was hand-waved. The first three are resolved in the design above; (4) remains an Open Question targeted at spec time.
