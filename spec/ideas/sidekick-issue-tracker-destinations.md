# Idea: Sidekick Issue-Tracker Destinations

**Status:** Specified
**Date:** 2026-05-22
**Owner:** alexandertrakhimenok
**Promotes To:** issue-artifact-type
**Supersedes:** —
**Related Ideas:** extends:sidekick-ideas

## Problem Statement

How might we let captured sidekick artifacts — both ideas and reported issues — land directly in the team's existing issue tracker (GitHub first), with a thin local mirror that keeps the SpecScore graph intact, so teammate visibility and issue triage stop being side-effects of someone pulling the right branch?

## Context

Today `specstudio:sidekick` writes captured seeds to `spec/ideas/seeds/<slug>.md` only. That artifact is durable, lint-validated, and feeds the consilium pipeline cleanly — but it is invisible to teammates who haven't pulled the branch, invisible across machines until git syncs, and a poor fit for *issue* captures (observations of something broken) that the rest of the team already triages in GitHub Issues. The dogfood signal is concrete: the Idea author has wanted to drop an issue or teammate-visible idea into the GH issue tracker several times in the past week and instead wrote a local seed that no one else will see until merge. This is the same shape of pain that `idea-skills-destination-resolution` solved one layer down (which *repo* a seed lands in); this Idea is the analog one layer up (which *substrate* — local file vs. issue tracker). Prior art: most modern dev teams already centralize ideas and issue reports in GitHub Issues, Linear, or Jira; SpecScore's local-file-first stance is correct for the spec graph but wrong as a *capture* default in collaborative repos. The parent Idea `sidekick-ideas` already establishes that capture is woven into host skills and that the seed file is the canonical local record; this Idea extends Layer 1 (Capture) with a destination axis without touching Layers 2–3 (Synchestra queue + consilium). The taxonomy this Idea adopts: **issue = a reported observation of something wrong**, captured imprecisely at mid-flow (this Idea ships it); **bug = a specific defect identified by root cause analysis**, deferred to sibling Idea `bug-artifact-and-rca`. Most issue trackers conflate the two; SpecScore separates them on the same axis it already separates `sidekick-seed → Idea` on the forward-looking side.

## Recommended Direction

Add a **destination axis** to `specstudio:sidekick` plus a new **top-level `issue` artifact type**, both configured per-project in `specscore.yaml` under a new `sidekick:` block. Four design pillars. **Pillar 1 — Issue as a first-class SpecScore artifact type (with optional Feature-scoping).** Issues are introduced as a new top-level artifact, parallel to Ideas, Features, Plans, and Tasks — *not* a sub-type of `sidekick-seed`. An **issue** is a reported observation of something wrong (coarse, captured mid-flow, imprecise); it is explicitly *not* the same thing as a **bug** (which is a specific defect identified by root cause analysis). This Idea ships the `issue` artifact only; the `bug` artifact + RCA pipeline is deferred to a sibling Idea (`bug-artifact-and-rca`, to be drafted). Issues have a distinct lifecycle (`open → investigating → resolved` on the happy path, or `open → rejected` when not-a-defect / won't-fix / duplicate / not-reproducible), and they do NOT go through the consilium review pipeline (you don't vote on whether an issue is real). An issue lives at one of two paths: `spec/issues/<slug>.md` (root-level — default for capture; the issue isn't yet tied to a specific Feature or spans multiple) or `spec/features/<feature-slug>/issues/<issue-slug>.md` (Feature-scoped — the issue is known to affect a specific Feature, typically discovered during dogfood or post-implementation). A `spec/issues/README.md` index lists root-level issues; each Feature directory MAY contain an `issues/README.md` index of its own issues. Issue frontmatter is fixed: `type: issue`, `slug`, `status` (one of `open|investigating|resolved|rejected`), `captured_at`, `captured_by`, `severity` (low/medium/high/critical — *perceived* severity at report time), `steps_to_reproduce`, optional `affected_component` (Feature slug when known), optional `first_seen` (commit SHA or version), optional `github_issue` (URL/number after GH mirror), optional `rejection_reason` (required when `status: rejected`), and a reserved `bugs: []` list (filled by the future bug-artifact-and-rca surface; remains empty in this Idea's MVP). Lint adds an `issue` artifact namespace (rule prefix `I-`). The `sidekick` skill gains `--type {idea|issue}` (default `idea`, preserving today's behavior). With `--type issue` and no `--feature`, captures write to `spec/issues/<slug>.md`. With `--type issue --feature <feature-slug>`, captures write to `spec/features/<feature-slug>/issues/<issue-slug>.md`. Caller specifies — no content classification at capture time, in line with sidekick's anti-content-deliberation rule. Relocation from root to Feature-scoped during triage is manual (mv + lint) in MVP; a future `specscore issue relocate` CLI verb is the natural follow-up (analog to `specscore idea relocate`). **Pillar 2 — Destination as configurable substrate.** New config under `sidekick:` with `destination: local|github|ask`, `strictness: strict|recommended`, and a `github:` sub-block carrying `repo` (default: `project.repo` from `specscore.yaml`) and `labels` indexed by seed type. `strict` mode writes to the configured destination with no prompt. `recommended` mode shows the configured options at capture, pre-selecting the first (acceptable derail-cost because the user opted into it). Per-invocation `--destination {local|github|ask}` always overrides. Default for new projects ships `local` + `strict` — today's behavior preserved. **Pillar 3 — Mirror as the default sync model.** When `destination: github`, the skill writes **both** the local seed AND opens a GitHub Issue. The local seed remains canonical for the SpecScore graph; its frontmatter carries the issue URL and number. The issue body is the seed's raw markdown verbatim — title becomes the issue title, body becomes the issue body, the seed's YAML frontmatter is wrapped in an HTML comment so GH's renderer hides it but tooling can round-trip. A footer line on the issue links back to the seed at its repo path. The local seed's body carries a brief one-line summary plus the issue URL — enough that opening the local file tells a reader "this lives in GH issue #123, summary: ___" without duplicating the full body in two places that will drift. **Pillar 4 — Two-way sync is the GitHub App's job, not the skill's.** The capture-time write is one-way (local + GH at capture). Drift after that — issue comments, status changes, edits — is the surface for a future *SpecScore GitHub App*. On the first `github` destination capture per workspace, the skill prints a one-time, dismissable invitation: "Install the SpecScore GitHub App to keep seeds and issues in sync." The invitation is dismissable forever per workspace, never blocks the capture, and is the only marketing surface in the skill. The unchanging contract: `sidekick-idea.captured` event still fires with the local seed path; consilium and `specscore:whats-next` don't change. The destination axis is additive to Layer 1 of the parent Idea; Layers 2–3 are untouched.

## Alternatives Considered

**GitHub-only, no local seed.** Skip the local file entirely; the GH Issue is the only artifact. *Lost because:* it breaks the SpecScore graph. The consilium pipeline reads `spec/ideas/seeds/<slug>.md`; lint validates the same path; `specscore:whats-next` indexes the same path. Routing seeds out of the local tree would force every downstream consumer to learn a remote-fetch path, and the system would only work online. Mirror — local canonical, GH as projection — preserves Layer 2–3 contracts at the cost of one extra small file write.

**Pointer-only local file.** The local seed contains only the GH issue URL and a one-line title; the issue body holds the real content. *Lost because:* it pushes the same online dependency one layer deeper. Lint can still parse the pointer, but the consilium briefing pack would need to fetch GH to assemble facts, and the whole system breaks for users without GH auth at consilium time. The "brief summary + URL in seed body" middle path keeps the local file useful as a standalone record while not duplicating the full body (avoiding drift).

**Issue as a sub-type of `sidekick-seed` (early framing of this Idea, since rejected).** Treat reports as `type: bug-seed` within `spec/ideas/seeds/`, sharing the existing capture pipeline and consilium review. *Lost because:* the lifecycles don't match. Idea seeds get *deliberated* (does this idea deserve to become a Feature?); issues get *investigated and resolved or rejected* — you don't vote on whether a reported defect is real. Forcing issues through the consilium pipeline means the panel either rubber-stamps them (waste of tokens) or worse, votes "should-not-implement" on a legitimate issue because it's not worth the engineering cost (catastrophic — broken behavior isn't a feature request). Putting issues in `spec/ideas/seeds/` also reads wrong semantically: issues are observations about the *present* state of the system; ideas are speculation about the *future*. A top-level `issue` artifact with its own lifecycle separates the two cleanly.

**Conflate issue and bug into a single artifact named "bug".** Original draft of this revision called the new artifact `bug`. *Lost because:* "bug" in rigorous engineering vocabulary means a *specific defect identified by root cause analysis*, not a report of broken behavior. Most issue trackers conflate the two and pay a cost for it (every "bug ticket" silently mixes the *report* — "menu crashes" — with the *defect* — "null deref in parseMenu line 142"). The `issue → bug` split mirrors the existing `sidekick-seed → Idea` split on the forward-looking side: capture-time observation vs. investigation-result. This Idea ships only the `issue` half; the `bug` artifact + RCA pipeline becomes a sibling Idea (`bug-artifact-and-rca`). The `issue` schema reserves a `bugs: []` field from day one so the future link is purely additive.

**Ship both `issue` and `bug` artifacts in this MVP.** Define the full RCA pipeline (issue → 0..N bugs, with link integrity, bug lifecycle, possibly a `specstudio:rca` skill) within this Idea. *Lost because:* the RCA workflow has real design surface — who creates bugs, when, with what context, how the issue closes when bugs verify — and smuggling it into this Idea's MVP would either bloat the scope past what dogfood can validate in two weeks, or under-design the RCA path. Deferring to a sibling Idea lets each artifact earn its complexity. Forward-compatibility is preserved via the reserved `bugs: []` field on `issue`.

**One unified seed schema with optional issue fields.** Add `steps_to_reproduce`, `severity`, `affected_component` as optional frontmatter on the existing seed type; no sub-type and no new artifact. *Lost because:* same lifecycle-mismatch problem as the sub-type alternative, plus lint becomes weaker (can't enforce "issues must have steps_to_reproduce"). Schema flexibility without lifecycle clarity is the worst of both.

**Issues only under Features (no root-level path).** Force every issue to live at `spec/features/<feature-slug>/issues/<issue-slug>.md` — no `spec/issues/<slug>.md`. *Lost because:* at capture time the user often doesn't know which Feature the issue belongs to (or the issue is cross-cutting), and forcing the decision upfront breaks the sidekick "write-and-continue" discipline. Root-level capture with optional later relocation matches how triage actually works.

**Issues only at root (no Feature-scoped path).** Single location, all issues at `spec/issues/<slug>.md`. *Lost because:* once an issue is triaged to a specific Feature, co-locating it with that Feature's other artifacts makes the Feature's spec directory a richer single source of truth — `specscore feature info <slug>` can list known issues alongside ACs. The cost is one extra valid path; lint and the issue schema are otherwise identical.

**Always-ask destination at capture time.** Skip the per-project default and prompt every time. *Lost because:* it conflicts with the parent Idea's "write-and-continue" discipline — every prompt is a derail. The `strictness: recommended` mode preserves the option for users who want it, but the default is `strict` so the common case stays one-shot.

**Adapter abstraction layer up-front (GitHub + GitLab + Jira behind one interface).** Build the destination axis generic from day one. *Lost because:* premature generalization with no validated demand. Three adapters cost more than three times one adapter (auth strategies, API shapes, label/template conventions all differ). The four-pillar design names "GitHub first" deliberately; the bug-seed schema and destination axis are general enough to host a future adapter, but no adapter contract is frozen until the GitHub one has earned it.

## MVP Scope

**One vertical slice that earns its keep on the author's machine within a week.** A user types `/sidekick --type issue 'crash on empty seed dir'` in a project where `specscore.yaml` has `sidekick.destination: github` and `sidekick.strictness: strict`. The skill writes `spec/issues/crash-on-empty-seed-dir.md` with `type: issue` frontmatter (containing the GH issue number and URL once the call returns), opens issue #N in the project's GH repo with the artifact body as the issue body, emits `sidekick-idea.captured` (with new `artifact_type: issue` and `feature_slug: null` payload fields) carrying the issue path, and prints `Captured → spec/issues/crash-on-empty-seed-dir.md · gh#N` in under 1.5s p95 with `gh` CLI already authenticated. The parallel `/sidekick --type issue --feature sidekick-capture 'crash on empty seed dir'` writes to `spec/features/sidekick-capture/issues/crash-on-empty-seed-dir.md` instead. `recommended` strictness, `--destination ask` per-invocation flag, the dismissable GitHub App invitation, the `issue` artifact's lint rules (`I-001` onward), and the `spec/issues/README.md` index are all in MVP. **What is explicitly NOT in MVP:** the `bug` artifact + RCA pipeline (deferred to sibling Idea `bug-artifact-and-rca`); GitLab/Jira adapters; bidirectional sync; retroactive migration of existing local seeds; label/template customization beyond the `labels:` config; the GitHub App itself; a `specscore issue relocate` CLI verb (manual mv + lint works); a `specscore issue change-status` CLI verb (frontmatter edits work); the `issue.bugs[]` link surface (reserved in frontmatter but no link integrity until the sibling Idea ships). Success measurement after two weeks of dogfood: (a) ≥ 3 issues captured that a teammate engaged with on GitHub (comment/close/reassign) — visibility-win signal; (b) zero observed cases where the GH write derailed the host skill (latency or auth prompt breaks "write-and-continue"); (c) the author no longer writes issues manually into the GH UI when in the middle of a host-skill flow; (d) at least one root-level issue gets relocated to Feature-scoped during triage, and at least one gets transitioned to `rejected` with a recorded `rejection_reason` — the dual-location and the rejection path are both exercised.

## Not Doing (and Why)

- GitLab and Jira adapters — validate adoption on GitHub first; the destination axis is designed to extend cleanly but other adapters wait on demand.
- Bidirectional sync between seed and issue — that is the SpecScore GitHub App's job; the capture-time write is one-way by design.
- Auto-classify issue vs idea from content — caller specifies `--type`; matches sidekick's anti-content-deliberation rule.
- Retroactive migration of existing `spec/ideas/seeds/*.md` into GH issues or into the new `issue` artifact — separate one-off tool if it ever earns its keep.
- A `specscore issue relocate` CLI verb to move issues from root to Feature-scoped — manual `mv` + lint works for MVP; CLI verb is a clean follow-up.
- A `specscore issue change-status` CLI verb for `open → investigating → resolved` / `→ rejected` transitions — frontmatter edits work for MVP; CLI verb is a clean follow-up.
- The `bug` artifact, the issue→bug RCA pipeline, and the `issue.bugs[]` link integrity — deferred to sibling Idea `bug-artifact-and-rca`. The `bugs: []` field is reserved on `issue` frontmatter from day one so the future link is purely additive; lint MUST accept the empty list and MUST NOT yet validate referenced bug slugs.
- A consilium-like pipeline for issues — issues are not deliberated; they are investigated and resolved or rejected.
- Closing or updating GH-mirrored issues from the local skill — write-only at capture time; lifecycle changes happen in GH and (later) flow back via the App.
- Per-org auth management or token UI — assumes `gh` CLI authenticated or `GITHUB_TOKEN` env var; clean error if neither, with fallback to local-only on failure.
- Auto-derive labels from seed body content — labels come from the `sidekick.github.labels` config, indexed by seed type.

## Key Assumptions to Validate

| Tier | Assumption | How to validate |
|------|------------|-----------------|
| Must-be-true | The "write-and-continue" discipline survives a GH API round-trip. Capture-to-host-resumption latency stays low enough that the host skill doesn't feel derailed. | Measure end-to-end capture latency over 30 dogfood captures with `gh` CLI auth ready. Target ≤ 1.5s p95. If exceeded, the GH write must be backgrounded with the local seed acting as the immediate-write checkpoint. |
| Must-be-true | The teammate-visibility win is real: GH-mirrored issues get teammate engagement that local-only artifacts never would. | Run for two weeks with `destination: github` on this repo. Count GH-side engagement events (comment, label change, close, reassign) on sidekick-opened issues. ≥ 30% engagement-within-7-days is the threshold; below that, the mirror is paperwork. |
| Must-be-true | Round-tripping the seed via an HTML-comment-wrapped frontmatter survives both GH's renderer and any future GH App parser without corruption. | Round-trip 10 seeds end-to-end (write to GH, fetch via GH API, re-parse frontmatter). All frontmatter fields must match byte-for-byte modulo whitespace; rendered issue must hide the comment in the GH UI. |
| Should-be-true | Issues and ideas genuinely need distinct lifecycles. After 20 mixed captures (10 each), issues flow through `open → investigating → resolved` (or `open → rejected`) and ideas flow through the consilium-or-direct-to-Feature path, with no observed cross-contamination (issues accidentally consilium-reviewed, ideas accidentally marked "resolved"). | Audit the 20 captures: percent of issue artifacts in `spec/issues/` (or Feature-scoped) ≥ 95%, percent of issue-resolved-or-rejected lifecycle events ≥ 80%, zero consilium reviews triggered against issue artifacts. If issues end up in the consilium queue or ideas end up at `spec/issues/`, the dispatch rule needs tightening. |
| Should-be-true | The dual-location design (root vs Feature-scoped) earns its keep. A meaningful fraction of root-level issues get relocated to Feature-scoped during triage, AND a meaningful fraction stay at root because they're cross-cutting or unassigned. | After two weeks: count root-issue relocations to Feature-scoped (target: ≥ 20% of issues), and count root-issues still at root after one week (target: ≥ 20%). If 100% relocate, Feature-scoped should be the only path. If 0% relocate, drop the Feature-scoped path. |
| Should-be-true | The issue-vs-bug taxonomy is the right split, even though the `bug` artifact isn't in this MVP. The reserved `bugs: []` field on issues is used (manually filled) often enough during dogfood that the future `bug-artifact-and-rca` Idea has a real consumer. | After two weeks: count issues whose authors manually added a non-empty `bugs: []` (or wrote prose describing root-cause defects in the body). ≥ 20% should show RCA-shaped follow-up content. If 0%, the issue artifact alone covers the user's needs and `bug` may never be worth shipping. |
| Should-be-true | A brief one-line summary plus URL in the local seed body is enough to avoid duplication-drift without losing standalone readability of the local file. | After 10 captures, ask: when a reader opens the local seed, can they understand what the idea is about without clicking through to GH? If "must click through" > 30% of the time, the summary template is too thin. |
| Should-be-true | The dismissable GitHub App invitation is net-positive — it converts some users without annoying the rest. | Track install-rate per first-capture event, plus opt-out rate. ≥ 20% install OR ≥ 80% silent dismissal (no complaint, no skill abandonment) is acceptable. Negative signal: any user reports the invitation as friction in dogfood feedback. |
| Should-be-true | The destination axis stays additive — Layers 2–3 of the parent `sidekick-ideas` Idea (Synchestra queue, consilium) need zero changes to handle GH-mirrored seeds. | Run the existing consilium pipeline against a mix of local-only and GH-mirrored seeds; verify identical verdict shape, identical event emission, identical task-board behavior. Any divergence is a contract violation that means this Idea is touching Layer 2–3 surface area it shouldn't. |
| Might-be-true | The `recommended` strictness mode (show options, pre-select first) is used at all — i.e., a meaningful fraction of users want per-capture choice rather than per-project default. | After two weeks, count config values across dogfood users. If `recommended` is used by <10% of users who configured the block at all, drop the mode and ship strict-only. |
| Might-be-true | Issues don't want the 30-day content-hash dedupe that idea seeds use (separate reporters legitimately re-file the same issue; the dedupe is noise-suppression for ideas, not for issue reports). | Inspect issue collisions over the first month; tag each as legitimate re-report or noise. If legitimate re-reports outnumber noise, disable the dedupe for `issue` type. |


## SpecScore Integration

- **New Features this would create:**
  - `sidekick-destination-routing` — the destination axis in `specscore.yaml` (`sidekick.destination`, `sidekick.strictness`, `sidekick.github`), the `--destination` and `--type` flags on the sidekick skill, the strict-vs-recommended resolution logic, and the GitHub Issue writer.
  - `issue-artifact-type` — introduces `issue` as a top-level SpecScore artifact type parallel to Ideas/Features/Plans/Tasks. Covers the `issue` schema (frontmatter contract: `type`, `slug`, `status`, `captured_at`, `captured_by`, `severity`, `steps_to_reproduce`, optional `affected_component`, `first_seen`, `github_issue`, `rejection_reason`, reserved `bugs: []`), the dual-location convention (`spec/issues/<slug>.md` root + `spec/features/<feature-slug>/issues/<issue-slug>.md` Feature-scoped), the `spec/issues/README.md` index spec, the `I-001`-prefixed lint rules, and the issue lifecycle states (`open → investigating → resolved` happy path, or `open → rejected` with required `rejection_reason`). Lifecycle transitions are manual frontmatter edits in MVP; CLI verb (`specscore issue change-status`) is a follow-up.
  - `github-app-sync` (deferred, post-MVP, separate Idea) — the SpecScore GitHub App that keeps captured artifacts and GH issues in sync (comments → artifact updates, GH-issue close → artifact `status: resolved`, etc.). Out of MVP; named here only so the marketing surface in Pillar 4 has somewhere to point.
  - `bug-artifact-and-rca` (deferred sibling Idea, to be drafted) — introduces the `bug` artifact type, the issue→bug RCA pipeline, the `issue.bugs[]` ↔ `bug.causes_issues[]` link integrity, and possibly a `specstudio:rca` skill. Not part of this Idea's surface; named here so the reserved `issue.bugs: []` field has a documented future home.
- **Existing Features affected:**
  - `sidekick-capture` (specstudio) — extends the skill's input surface (`--type {idea|issue}`, `--destination`, `--feature <slug>` when `--type issue`), adds the destination-resolution step before the file write, dispatches to the right artifact path based on `--type` + `--feature` (idea → `spec/ideas/seeds/`, root issue → `spec/issues/`, Feature-scoped issue → `spec/features/<slug>/issues/`), adds the GH Issue writer when destination is `github`, and writes the GH issue URL back into the captured artifact's frontmatter. The `sidekick-idea.captured` event payload gains an `artifact_type` field (`idea-seed` | `issue`) and a `feature_slug` field (nullable) so downstream consumers can route correctly.
  - `specscore spec lint` — gains the `I-` rule namespace for the new `issue` artifact (schema validation at both `spec/issues/<slug>.md` and `spec/features/<feature-slug>/issues/<issue-slug>.md`); existing `sidekick-seed` lint rules apply unchanged for idea captures.
  - `specscore feature info <slug>` (existing) — gains a "Known issues" section listing Feature-scoped issues alongside ACs.
  - `specstudio:init` — when the user enables a GH destination during init, the wizard prompts for `sidekick.destination`, `strictness`, and `github.repo` defaults and writes them to `specscore.yaml`.
  - `specscore:whats-next` — surfaces remote-mirrored seeds with the GH URL alongside the local path. No behavior change beyond rendering.
- **Dependencies:**
  - Parent Idea `sidekick-ideas` (Layer 1 is the extension point).
  - Sibling Idea `idea-skills-destination-resolution` (resolves *which* repo; this Idea resolves *which substrate within* that repo).
  - `gh` CLI on the developer's machine, or `GITHUB_TOKEN` env var. Clean error + local-only fallback if neither is present.
  - GitHub REST API v3 (issue create) — already covered by `gh issue create`.

## Open Questions

- **GH auth failure policy.** If `gh` CLI is not authenticated and `GITHUB_TOKEN` is unset, does the skill (a) abort the whole capture (consistent: nothing is recorded), (b) fall back to local-only with a printed warning (graceful: the seed survives), or (c) write local and queue the GH write for retry? Current lean: (b) — the local seed is the canonical record anyway, and "write-and-continue" beats "abort on a side channel failure". Validate during MVP dogfood.
- **GH issue title formatting.** Today the captured artifact's H1 is the one-liner verbatim. Should the GH issue title be (a) the one-liner verbatim, (b) prefixed by artifact type (`[issue] ...` vs `[idea] ...`), or (c) follow the repo's own issue template title convention if one exists? Current lean: (a) for MVP; convention-detection is a follow-up.
- **Repo issue templates.** GitHub repos commonly carry issue templates under `.github/ISSUE_TEMPLATE/`. Does the SpecScore writer (a) ignore them and write our raw markdown, (b) detect them and use the closest match, or (c) require a `sidekick.github.template` config pointing at a specific template? Current lean: (a) for MVP — the raw SpecScore markdown is the contract; template integration is a follow-up if users ask.
- **Consilium → issue comment surface.** When (or if) the future consilium runs against a GH-mirrored seed, should the Panel summary be appended as a comment on the GH issue rather than only written to the local seed? This is more about the consilium's destination awareness than this Idea's MVP, but the contract decision belongs here: does the local seed's `synchestra_task` field grow a sibling `github_issue` reference that downstream consumers (like the consilium) can read and target? Current lean: yes — frontmatter is the integration surface; consilium reads it and decides.
- **Destination-axis interplay with `idea-skills-destination-resolution`.** That sibling Idea picks *which local repo* a seed lands in via sibling-dir scan. Order of operations: pick local repo first (existing), then within that repo's `specscore.yaml` read `sidekick.destination` and decide substrate. Confirmed-by-design but worth naming so the two routing decisions don't collide in the same prompt.
- **Workspace-level "seen the GH App invitation" state.** The dismissal flag for the GitHub App invitation needs to live somewhere. Project-local file (e.g. `.specscore/state.json`) is the obvious answer; global user-level state would be wrong (invitation should re-show in a new workspace). Confirm during implementation.
- **Issue relocation mechanic.** How does an issue move from root (`spec/issues/<slug>.md`) to Feature-scoped (`spec/features/<feature-slug>/issues/<issue-slug>.md`) during triage? MVP says manual `mv` + lint; the open question is whether the natural follow-up CLI verb is `specscore issue relocate` (analog to existing `specscore idea relocate`) or `specscore issue change-status --to=investigating --feature=<slug>` (status-and-location in one transition). Lean: separate verbs — relocation is orthogonal to status.
- **Issue-side index hygiene.** `spec/issues/README.md` lists root-level issues; each `spec/features/<feature-slug>/issues/README.md` lists Feature-scoped issues. Do we ship an `--all-issues` view that aggregates both into one virtual list (e.g. `specscore issue list`)? Open. Lean: yes for MVP-discovery, but it's a CLI surface not an index file.
- **Reverse-link drift between Feature-scoped issue and parent Feature.** When an issue at `spec/features/<feature-slug>/issues/<issue-slug>.md` is added, should the parent Feature's README gain an auto-managed "Known issues" section (similar to how Ideas grow `Promotes To`)? Or is the directory listing sufficient? Lean: directory listing for MVP; auto-managed section is a `specscore lint --fix` follow-up.
- **Issue capture into a non-existent Feature directory.** If a user runs `/sidekick --type issue --feature nonexistent-slug`, does the skill (a) reject with "Feature not found", (b) write to `spec/issues/` and warn, or (c) create the Feature directory? Lean: (a) — the user typo'd; explicit error beats silent recovery.
- **`rejection_reason` taxonomy.** Should `rejection_reason` be a free-form string or constrained to an enum (`not-a-defect|wont-fix|duplicate|not-reproducible|by-design`)? Free-form is more flexible; enum is queryable and aligns with how mature trackers categorize. Lean: enum + optional free-form notes field; decide at Feature spec time.
- **Premature lint validation of `bugs: []`.** The field is reserved but the `bug` artifact doesn't exist yet. Should lint reject *any* non-empty `bugs: []` on issues in this Idea's MVP (since referenced bug slugs would resolve to nothing), or should it accept the field as opaque and defer validation to the sibling Idea? Lean: accept-as-opaque — gives users a place to manually record root-cause hypotheses before formal `bug` artifacts exist, and the sibling Idea adds link integrity later as a strictly-stronger rule.
