# Idea: Sidekick Issue-Tracker Destinations

**Status:** Approved
**Date:** 2026-05-22
**Owner:** alexandertrakhimenok
**Promotes To:** —
**Supersedes:** —
**Related Ideas:** extends:sidekick-ideas

## Problem Statement

How might we let captured sidekick seeds — both idea-shaped and bug-shaped — land directly in the team's existing issue tracker (GitHub first), with a thin local mirror that keeps the SpecScore graph intact, so teammate visibility and bug triage stop being side-effects of someone pulling the right branch?

## Context

Today `specstudio:sidekick` writes captured seeds to `spec/ideas/seeds/<slug>.md` only. That artifact is durable, lint-validated, and feeds the consilium pipeline cleanly — but it is invisible to teammates who haven't pulled the branch, invisible across machines until git syncs, and a poor fit for *bug* captures that the rest of the team already triages in GitHub Issues. The dogfood signal is concrete: the Idea author has wanted to drop a bug or teammate-visible idea into the GH issue tracker several times in the past week and instead wrote a local seed that no one else will see until merge. This is the same shape of pain that `idea-skills-destination-resolution` solved one layer down (which *repo* a seed lands in); this Idea is the analog one layer up (which *substrate* — local file vs. issue tracker). Prior art: most modern dev teams already centralize ideas/bugs in GitHub Issues, Linear, or Jira; SpecScore's local-file-first stance is correct for the spec graph but wrong as a *capture* default in collaborative repos. The parent Idea `sidekick-ideas` already establishes that capture is woven into host skills and that the seed file is the canonical local record; this Idea extends Layer 1 (Capture) with a destination axis without touching Layers 2–3 (Synchestra queue + consilium).

## Recommended Direction

Add a **destination axis** to `specstudio:sidekick` plus a **bug-seed sub-type**, both configured per-project in `specscore.yaml` under a new `sidekick:` block. Four design pillars. **Pillar 1 — Bug seeds as a distinct sub-type.** Today's seed schema is idea-shaped (one-liner + free-form body). Bugs benefit from a small fixed set of fields: `steps_to_reproduce`, `severity`, `affected_component`, optional `first_seen`. The `sidekick` skill gains `--type {idea|bug}` (default `idea`, preserving today's behavior). Lint learns a `bug-seed` variant of the existing `sidekick-seed` type. Caller specifies — no content classification at capture time, in line with the skill's anti-content-deliberation rule. **Pillar 2 — Destination as configurable substrate.** New config under `sidekick:` with `destination: local|github|ask`, `strictness: strict|recommended`, and a `github:` sub-block carrying `repo` (default: `project.repo` from `specscore.yaml`) and `labels` indexed by seed type. `strict` mode writes to the configured destination with no prompt. `recommended` mode shows the configured options at capture, pre-selecting the first (acceptable derail-cost because the user opted into it). Per-invocation `--destination {local|github|ask}` always overrides. Default for new projects ships `local` + `strict` — today's behavior preserved. **Pillar 3 — Mirror as the default sync model.** When `destination: github`, the skill writes **both** the local seed AND opens a GitHub Issue. The local seed remains canonical for the SpecScore graph; its frontmatter carries the issue URL and number. The issue body is the seed's raw markdown verbatim — title becomes the issue title, body becomes the issue body, the seed's YAML frontmatter is wrapped in an HTML comment so GH's renderer hides it but tooling can round-trip. A footer line on the issue links back to the seed at its repo path. The local seed's body carries a brief one-line summary plus the issue URL — enough that opening the local file tells a reader "this lives in GH issue #123, summary: ___" without duplicating the full body in two places that will drift. **Pillar 4 — Two-way sync is the GitHub App's job, not the skill's.** The capture-time write is one-way (local + GH at capture). Drift after that — issue comments, status changes, edits — is the surface for a future *SpecScore GitHub App*. On the first `github` destination capture per workspace, the skill prints a one-time, dismissable invitation: "Install the SpecScore GitHub App to keep seeds and issues in sync." The invitation is dismissable forever per workspace, never blocks the capture, and is the only marketing surface in the skill. The unchanging contract: `sidekick-idea.captured` event still fires with the local seed path; consilium and `synchestra:whats-next` don't change. The destination axis is additive to Layer 1 of the parent Idea; Layers 2–3 are untouched.

## Alternatives Considered

**GitHub-only, no local seed.** Skip the local file entirely; the GH Issue is the only artifact. *Lost because:* it breaks the SpecScore graph. The consilium pipeline reads `spec/ideas/seeds/<slug>.md`; lint validates the same path; `synchestra:whats-next` indexes the same path. Routing seeds out of the local tree would force every downstream consumer to learn a remote-fetch path, and the system would only work online. Mirror — local canonical, GH as projection — preserves Layer 2–3 contracts at the cost of one extra small file write.

**Pointer-only local file.** The local seed contains only the GH issue URL and a one-line title; the issue body holds the real content. *Lost because:* it pushes the same online dependency one layer deeper. Lint can still parse the pointer, but the consilium briefing pack would need to fetch GH to assemble facts, and the whole system breaks for users without GH auth at consilium time. The "brief summary + URL in seed body" middle path keeps the local file useful as a standalone record while not duplicating the full body (avoiding drift).

**One unified seed schema with optional bug fields.** Add `steps_to_reproduce`, `severity`, `affected_component` as optional frontmatter on the existing seed type; no sub-type. *Lost because:* lint becomes weaker (it can't enforce "bugs must have steps_to_reproduce"), the consilium's expert panel can't reason about seed type without parsing optional fields, and downstream tooling (e.g. routing labels in the new `sidekick.github.labels` map) lacks a clean key. A distinct `bug-seed` sub-type keeps each schema sharp; the cost is one new lint rule and one new template.

**Always-ask destination at capture time.** Skip the per-project default and prompt every time. *Lost because:* it conflicts with the parent Idea's "write-and-continue" discipline — every prompt is a derail. The `strictness: recommended` mode preserves the option for users who want it, but the default is `strict` so the common case stays one-shot.

**Adapter abstraction layer up-front (GitHub + GitLab + Jira behind one interface).** Build the destination axis generic from day one. *Lost because:* premature generalization with no validated demand. Three adapters cost more than three times one adapter (auth strategies, API shapes, label/template conventions all differ). The four-pillar design names "GitHub first" deliberately; the bug-seed schema and destination axis are general enough to host a future adapter, but no adapter contract is frozen until the GitHub one has earned it.

## MVP Scope

**One vertical slice that earns its keep on the author's machine within a week.** A user types `/sidekick --type bug 'crash on empty seed dir'` in a project where `specscore.yaml` has `sidekick.destination: github` and `sidekick.strictness: strict`. The skill writes `spec/ideas/seeds/crash-on-empty-seed-dir.md` with bug-shaped frontmatter (containing the issue number and URL once the GH call returns), opens issue #N in the project's GH repo with the seed body as the issue body, emits `sidekick-idea.captured` with the seed path (unchanged contract), and prints `Captured → spec/ideas/seeds/crash-on-empty-seed-dir.md · gh#N` in under 1.5s p95 with `gh` CLI already authenticated. `recommended` strictness, `--destination ask` per-invocation flag, the dismissable GitHub App invitation, and the bug-seed lint variant are all in MVP. **What is explicitly NOT in MVP:** GitLab/Jira adapters, bidirectional sync, retroactive migration of existing local seeds, label/template customization beyond the `labels:` config, the GitHub App itself. Success measurement after two weeks of dogfood: (a) ≥ 3 bug seeds captured that a teammate engaged with on GitHub (comment/close/reassign) — this is the visibility-win signal; (b) zero observed cases where the GH write derailed the host skill (latency or auth prompt breaks "write-and-continue"); (c) the author no longer writes bugs manually into the GH UI when in the middle of a host-skill flow.

## Not Doing (and Why)

- GitLab and Jira adapters — validate adoption on GitHub first; the destination axis is designed to extend cleanly but other adapters wait on demand.
- Bidirectional sync between seed and issue — that is the SpecScore GitHub App's job; the capture-time write is one-way by design.
- Auto-classify bug vs idea from content — caller specifies `--type`; matches sidekick's anti-content-deliberation rule.
- Retroactive migration of existing `spec/ideas/seeds/*.md` into GH issues — separate one-off tool if it ever earns its keep.
- Closing or updating issues from the local skill — write-only at capture time; lifecycle changes happen in GH and (later) flow back via the App.
- Per-org auth management or token UI — assumes `gh` CLI authenticated or `GITHUB_TOKEN` env var; clean error if neither, with fallback to local-only on failure.
- Auto-derive labels from seed body content — labels come from the `sidekick.github.labels` config, indexed by seed type.

## Key Assumptions to Validate

| Tier | Assumption | How to validate |
|------|------------|-----------------|
| Must-be-true | The "write-and-continue" discipline survives a GH API round-trip. Capture-to-host-resumption latency stays low enough that the host skill doesn't feel derailed. | Measure end-to-end capture latency over 30 dogfood captures with `gh` CLI auth ready. Target ≤ 1.5s p95. If exceeded, the GH write must be backgrounded with the local seed acting as the immediate-write checkpoint. |
| Must-be-true | The teammate-visibility win is real: GH-mirrored seeds get teammate engagement that local-only seeds never would. | Run for two weeks with `destination: github` on this repo. Count GH-side engagement events (comment, label change, close, reassign) on sidekick-opened issues. ≥ 30% engagement-within-7-days is the threshold; below that, the mirror is paperwork. |
| Must-be-true | Round-tripping the seed via an HTML-comment-wrapped frontmatter survives both GH's renderer and any future GH App parser without corruption. | Round-trip 10 seeds end-to-end (write to GH, fetch via GH API, re-parse frontmatter). All frontmatter fields must match byte-for-byte modulo whitespace; rendered issue must hide the comment in the GH UI. |
| Should-be-true | Bug seeds and idea seeds genuinely need distinct schemas. After 20 mixed captures (10 each), the bug-specific fields are filled and consulted by downstream consumers (consilium expert prompts, lint, future routing). | Audit the 20 seeds: percent of bug seeds with non-empty `steps_to_reproduce` ≥ 80%, and the consilium's bug-aware expert prompts (when they exist) reference the field. If bug-specific fields stay empty or unread, collapse back into one schema with optional fields. |
| Should-be-true | A brief one-line summary plus URL in the local seed body is enough to avoid duplication-drift without losing standalone readability of the local file. | After 10 captures, ask: when a reader opens the local seed, can they understand what the idea is about without clicking through to GH? If "must click through" > 30% of the time, the summary template is too thin. |
| Should-be-true | The dismissable GitHub App invitation is net-positive — it converts some users without annoying the rest. | Track install-rate per first-capture event, plus opt-out rate. ≥ 20% install OR ≥ 80% silent dismissal (no complaint, no skill abandonment) is acceptable. Negative signal: any user reports the invitation as friction in dogfood feedback. |
| Should-be-true | The destination axis stays additive — Layers 2–3 of the parent `sidekick-ideas` Idea (Synchestra queue, consilium) need zero changes to handle GH-mirrored seeds. | Run the existing consilium pipeline against a mix of local-only and GH-mirrored seeds; verify identical verdict shape, identical event emission, identical task-board behavior. Any divergence is a contract violation that means this Idea is touching Layer 2–3 surface area it shouldn't. |
| Might-be-true | The `recommended` strictness mode (show options, pre-select first) is used at all — i.e., a meaningful fraction of users want per-capture choice rather than per-project default. | After two weeks, count config values across dogfood users. If `recommended` is used by <10% of users who configured the block at all, drop the mode and ship strict-only. |
| Might-be-true | Bug seeds don't want the 30-day content-hash dedupe that idea seeds use (separate reporters legitimately re-file the same bug; the dedupe is noise-suppression for ideas). | Inspect bug-seed collisions over the first month; tag each as legitimate re-report or noise. If legitimate re-reports outnumber noise, disable the dedupe for `bug` type. |


## SpecScore Integration

- **New Features this would create:**
  - `sidekick-destination-routing` — the destination axis in `specscore.yaml` (`sidekick.destination`, `sidekick.strictness`, `sidekick.github`), the `--destination` and `--type` flags on the sidekick skill, the strict-vs-recommended resolution logic, and the GitHub Issue writer.
  - `bug-seed-schema` — the new `bug-seed` lint variant of `sidekick-seed`, with `steps_to_reproduce`, `severity`, `affected_component`, optional `first_seen` frontmatter fields; lint rule and template.
  - `github-app-sync` (deferred, post-MVP) — the SpecScore GitHub App that keeps seeds and issues in sync (comments → seed updates, issue close → seed status, etc.). Out of MVP; named here only so the marketing surface in Pillar 4 has somewhere to point.
- **Existing Features affected:**
  - `sidekick-capture` (specstudio) — extends the skill's input surface (`--type`, `--destination`), adds the destination-resolution step before the file write, adds the GH Issue writer when destination is `github`, and writes the issue URL back into the seed frontmatter. The `sidekick-idea.captured` event payload is unchanged.
  - `specscore spec lint` — recognizes the `bug-seed` variant; existing `sidekick-seed` lint rules apply unchanged.
  - `specstudio:init` — when the user enables a GH destination during init, the wizard prompts for `sidekick.destination`, `strictness`, and `github.repo` defaults and writes them to `specscore.yaml`.
  - `synchestra:whats-next` — surfaces remote-mirrored seeds with the GH URL alongside the local path. No behavior change beyond rendering.
- **Dependencies:**
  - Parent Idea `sidekick-ideas` (Layer 1 is the extension point).
  - Sibling Idea `idea-skills-destination-resolution` (resolves *which* repo; this Idea resolves *which substrate within* that repo).
  - `gh` CLI on the developer's machine, or `GITHUB_TOKEN` env var. Clean error + local-only fallback if neither is present.
  - GitHub REST API v3 (issue create) — already covered by `gh issue create`.

## Open Questions

- **GH auth failure policy.** If `gh` CLI is not authenticated and `GITHUB_TOKEN` is unset, does the skill (a) abort the whole capture (consistent: nothing is recorded), (b) fall back to local-only with a printed warning (graceful: the seed survives), or (c) write local and queue the GH write for retry? Current lean: (b) — the local seed is the canonical record anyway, and "write-and-continue" beats "abort on a side channel failure". Validate during MVP dogfood.
- **Issue title formatting.** Today the seed's H1 is the one-liner verbatim. Should the GH issue title be (a) the one-liner verbatim, (b) prefixed by seed type (`[bug] ...`), or (c) follow the repo's own issue template title convention if one exists? Current lean: (a) for MVP; convention-detection is a follow-up.
- **Repo issue templates.** GitHub repos commonly carry issue templates under `.github/ISSUE_TEMPLATE/`. Does the SpecScore writer (a) ignore them and write our raw markdown, (b) detect them and use the closest match, or (c) require a `sidekick.github.template` config pointing at a specific template? Current lean: (a) for MVP — the raw SpecScore markdown is the contract; template integration is a follow-up if users ask.
- **Consilium → issue comment surface.** When (or if) the future consilium runs against a GH-mirrored seed, should the Panel summary be appended as a comment on the GH issue rather than only written to the local seed? This is more about the consilium's destination awareness than this Idea's MVP, but the contract decision belongs here: does the local seed's `synchestra_task` field grow a sibling `github_issue` reference that downstream consumers (like the consilium) can read and target? Current lean: yes — frontmatter is the integration surface; consilium reads it and decides.
- **Destination-axis interplay with `idea-skills-destination-resolution`.** That sibling Idea picks *which local repo* a seed lands in via sibling-dir scan. Order of operations: pick local repo first (existing), then within that repo's `specscore.yaml` read `sidekick.destination` and decide substrate. Confirmed-by-design but worth naming so the two routing decisions don't collide in the same prompt.
- **Workspace-level "seen the GH App invitation" state.** The dismissal flag for the GitHub App invitation needs to live somewhere. Project-local file (e.g. `.specscore/state.json`) is the obvious answer; global user-level state would be wrong (invitation should re-show in a new workspace). Confirm during implementation.
