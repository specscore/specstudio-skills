## Problem Statement

How might we automatically score the quality of retrofit output against ground-truth specs so we can iterate retrofit prompts and architecture against a real signal — instead of shipping retrofit blind and letting AC-quality regressions reach users?

## Context

Born from the pre-approval review of `retrofit-skill` (see `spec/ideas/retrofit-skill.md` Review Notes) and a follow-up user direction. The Test Engineer review explicitly called out the absence of a feedback loop on AC quality — Phase C approves the candidate Feature list, Phase D drafts ACs and exits with no verification gate, leaving the most error-prone step ungated. The user then identified that this loop deserves its own skill rather than being baked into retrofit (because a producer cannot fairly grade itself). Family context: `survey-skill` (activation hook) → `retrofit-skill` (opt-in deep path) → `retrofit-evaluation-skill` (this; internal quality loop). Without an automated grader, retrofit's quality is invisible to the team improving it — every prompt change is a guess.

## Recommended Direction

An internal-facing specstudio skill — `specstudio:retrofit-evaluation` (proposed rename to `specstudio:grade`, see Open Questions) — that consumes (1) a sandbox directory of retrofit output produced via retrofit's `--ignore-existing-specs --output-dir` calibration mode, and (2) a ground-truth `spec/features/` tree. Produces a structured quality report (markdown rendered from a JSON source, same JSON-first discipline as survey-skill).

**Scoring dimensions:**

- **(a) Coverage** — **hierarchy-aware bipartite matching** (Hungarian assignment with a similarity threshold) between ground-truth Features and retrofit Features. Similarity score is a **single scalar** computed as a weighted sum: `sim = 0.4 * source_pointer_jaccard + 0.4 * embedding_cosine(title + one_liner) + 0.2 * (1 - normalized_tree_distance)`. Weights configurable; defaults shown. **Tree distance** is operationalized as **normalized path-edit distance** on the Feature hierarchy graph: edit distance between the two Feature's parent-chains (insertions, deletions, swaps), divided by the maximum possible distance for the two trees being compared (so the value is always in [0, 1]). Same-parent pairs score 0; cousin pairs score >0; cross-branch swaps score near 1. A retrofit Feature that has the right title but the wrong parent (e.g. "Login" under "Sessions" instead of "Auth") scores lower than one with both right. Acceptance threshold for a match: `sim ≥ 0.6` (tunable). Reports **precision** (matched-retrofit / |retrofit|) and **recall** (matched-ground-truth / |ground-truth|) separately, plus an explicit **unmatched-retrofit bucket** (retrofit Features that have no ground-truth counterpart — these feed Hallucination, not Coverage). Also reports a **hierarchy-correctness sub-score**: for matched pairs, what fraction have the same parent? F1 alone is forbidden; precision and recall *must* be reported separately because the asymmetry tells different failure stories (low recall = retrofit missed real Features; low precision = retrofit invented Features).
- **(b) AC faithfulness** — for each matched Feature pair, an LLM judge scores AC-equivalence pairwise. **Position-bias defense**: each pair is judged twice with order swapped; only consistent judgments count. The judge is an **ensemble of 2–3 different model families** (not just "different model" — see Cross-model below) with majority voting. The judge **independently verifies entailment from the cited source pointers** regardless of the retrofit AC's `derived-from` trailer — provenance trailers are producer-controlled metadata and cannot be trusted as ground truth.
- **(c) Hallucination rate** — counts (i) retrofit ACs where the judge cannot verify entailment from any cited source pointer regardless of `derived-from` label, (ii) `derived-from: [inferred]`-only ACs that are not explicitly flagged `classification: speculative` by retrofit, and (iii) all unmatched-retrofit Features from Coverage. Provenance trailers alone do not exempt an AC from hallucination scrutiny — the judge verifies the evidence chain end-to-end.
- **(d) DLP scrub effectiveness** (new, in response to retrofit-skill's claim that Phase 4 DLP scrub is not security theater) — graded against a planted-secrets corpus injected into the calibration repos at known locations. The corpus deliberately includes a **distractor set** of near-secret strings that should NOT be redacted (UUIDs, hashes, fake-looking constants, environment-variable names with no values) so precision is meaningful — without distractors, precision is trivially high. **Span-alignment for scoring** uses byte-range overlap: a scrub is a hit if its redacted span overlaps any planted-secret span at ≥50% of the planted span's bytes. Reports recall (fraction of planted secrets the scrub caught) and precision (fraction of scrub-redacted spans that actually overlap a planted secret rather than a distractor). Without this dimension, retrofit's DLP claim is unverified.
- **(e) Structural quality** — lint pass rate and required-section presence. Mechanical check, included for completeness.
- **(f) Gap-discovery quality** (new, in response to retrofit-skill's "researchers identify test gaps and edge cases" claim) — for each ground-truth Feature, how many of its ACs that *lacked* corresponding tests in the codebase did retrofit nevertheless produce as speculative ACs? **Identifying "ground-truth ACs without test backing"** uses a deterministic mapping: ground-truth ACs typically carry a `Verifies:` trailer (or equivalent provenance link) pointing to a test. ACs without such a trailer, OR ACs whose trailer points to a test that does not exist in the calibration corpus's HEAD, count as "gap ACs." If a calibration repo predates the `Verifies:` convention, the corpus owner adds the mapping by hand once during corpus prep — this is corpus assembly, not eval-time work. The metric is uncomputable on corpora without this mapping; eval refuses to score gap-discovery on such corpora rather than producing a bogus number. **gap-recall** = `|retrofit speculative ACs matched (via Coverage's bipartite matching) to a ground-truth gap AC| / |ground-truth gap ACs|`. **gap-precision** = `|retrofit speculative ACs matched to a ground-truth gap AC| / |retrofit speculative ACs that matched any ground-truth AC|`. The denominator deliberately excludes unmatched retrofit speculative ACs (those count as Hallucination, not low gap-precision). A third sub-metric, **gap-rediscovery rate**, reports `|retrofit speculative ACs that matched a ground-truth AC WITH test backing| / |total retrofit speculative ACs that matched any ground-truth AC|` — measures how often retrofit produces speculative ACs for behaviors that ground-truth already tests (i.e. retrofit didn't recognize the existing test). High rediscovery = retrofit isn't reading the tests carefully. High gap-recall means retrofit is finding the edge cases a thoughtful engineer would. Low gap-precision means retrofit is hallucinating speculative ACs that don't reflect real requirements.

**Status correctness is removed from the scored dimensions and demoted to a structural assertion.** Since retrofit-skill now defaults all retrofitted Features to `Implementing` and requires explicit human approval to mark `Stable`, the dimension collapses to "did the gate fire?" — a yes/no check rather than a graded metric.

**LLM-as-judge methodology:**

- **Metric:** judge-human agreement reported as **Cohen's κ** (or Krippendorff's α), not raw percentage agreement. Raw % is misleading on skewed-prior tasks. The Idea targets κ ≥ 0.6 (substantial agreement) on the AC-equivalence task; the previously-stated "≥80% agreement" is the *raw* threshold and is retained only as a sanity check.
- **Inter-human ceiling.** Before targeting any judge-human bar, calibrate inter-human agreement on the same task. If two humans only reach κ = 0.5 on AC-equivalence, judge-human κ ≥ 0.5 is the ceiling, not a floor. Reports both.
- **Cross-model ensemble.** "Different model family" is necessary but not sufficient — frontier models share enormous pretraining overlap and RLHF-converged preferences. Use an **ensemble of 2–3 judges (Claude + GPT-4o + Gemini, or equivalent)** with majority voting. Periodically **gold-standard against fresh human labels** (every release; small sample) to detect ensemble collusion.
- **Adversarial set.** Include a small set of *known-wrong* retrofit outputs (planted bugs, swapped ACs, hallucinated Features) in every grading run. If the ensemble fails to catch them, the judges are colluding; halt and re-calibrate.
- **Test-retest reliability.** Pin model versions, pin temperature to 0, run **n=3 per judgment** and report **median + IQR** rather than chasing tight reliability targets. ±5% test-retest was optimistic; 3–8% drift is typical even at temp 0.
- **Sample size.** Two repos with ~30 Features each (~60 AC pairs) is **statistically inert** — standard error swamps inter-iteration deltas. **Target ≥5 repos / ≥200 graded AC pairs** before claiming directional signal. Bootstrap CIs reported from day one.
- **Train/dev/test discipline.** Iterating retrofit prompts against the same calibration set is training-on-the-test-set. Declare **train / dev / held-out test splits** before the first iteration: train (prompt iteration), dev (intermediate validation), held-out (scored only at release gates). Without this split, score deltas measure memorization, not generalization. Held-out corpus is **never** used to inform prompt changes.

**Self-improvement loop:** run retrofit in calibration mode against the *train* corpus → run retrofit-evaluation → inspect report for systematic failure modes → adjust retrofit prompts or coordinator architecture → repeat, tracking score deltas across iterations. **Promote to held-out evaluation only at release gates** (every Nth iteration or before merging to main). The skill is internal — it is not pitched to retrofit's end users; it is the development tool the retrofit team uses to ship quality.

## Alternatives Considered

- **Manual review only (no automated grader).** Rejected. Doesn't scale, can't compare prompt iterations consistently across time, and humans grading the same output twice tend to disagree with themselves. Manual review remains the backstop for low-confidence cases — but the bulk has to be automatic for the loop to be useful.
- **Build the grader into retrofit itself.** Rejected. A producer cannot fairly grade its own output — same prompts and architecture share blind spots; the grader will systematically miss what retrofit systematically misses. Separation of producer and grader is the whole point.
- **Pure structural metrics (lint pass, section presence, AC count).** Rejected as the sole approach. Structural metrics are necessary but not sufficient — they measure form, not content fidelity. A retrofit run can produce lint-clean Features full of hallucinated ACs and pass every structural metric. Structural quality is one dimension; AC faithfulness and Coverage are the load-bearing ones.
- **LLM-as-judge using the same model retrofit uses.** Rejected. Same-model judges share failure modes with the producer. Use a different model tier (or family) for grading than the one retrofit's coordinator/researcher use. This is standard eval discipline.
- **Wrap an existing eval framework (promptfoo, deepeval, Inspect, LangChain Evals).** Strong candidate, not yet decided — see Open Questions. Wrapping is faster and inherits known judge prompts and stats infrastructure; building avoids dependency lock-in but reinvents capabilities. Default plan is to seriously evaluate one (likely Inspect from UK AISI for its provenance and design rigor) before committing to in-house build.
- **Embedding-based AC similarity as the equivalence signal.** Rejected as the primary signal. Embedding similarity captures surface similarity, not equivalence — two ACs can be embedding-near but semantically opposite (negation, edge-case inversion). Use embeddings for *matching* Features (Coverage), but use LLM-as-judge for *equivalence* of ACs (faithfulness). Different jobs, different tools.
- **Score deltas only, no absolute scoring.** Rejected. Deltas matter for the iteration loop, but absolute scores are needed to know when retrofit is "good enough to ship" — the gate criterion can't be expressed as a delta.

## MVP Scope

A three-week spike, started after retrofit-skill MVP exists. **Calibration corpus**: at minimum 5 repos producing ≥200 graded AC pairs (was previously 2 repos / ~60 pairs — statistically inert per the AI-Engineer re-review). Mandatory: `specstudio-skills` (with hand-written specs as ground truth), plus ≥1 ugly legacy repo the maintainer did not write. The 5-repo target requires identifying or commissioning the additional corpus before week 1 — that work starts in parallel with retrofit-skill MVP. **MVP report dimensions:** Coverage (precision + recall + unmatched-retrofit bucket), AC faithfulness (κ + raw agreement, with bootstrap CIs), Hallucination rate. DLP scrub effectiveness and Structural quality follow in v1.1; Status correctness is demoted to a structural assertion (not scored).

**Success criterion** (falsifiable, sharpened): on the held-out test corpus, the ensemble judge achieves Cohen's κ ≥ 0.6 against human labels on AC-equivalence (target ≥ inter-human ceiling, whichever is lower); precision and recall on Coverage each ≥ 0.7; hallucination rate ≤ 10%. Additionally: across 5 retrofit prompt iterations on the *train* corpus, the score-delta ordering matches a human reviewer's ranking of those iterations at ≥80% pairwise agreement. The held-out corpus is scored once at the end to validate generalization; not used to inform the iteration.

## Not Doing (and Why)

- User-facing surface — this is internal tooling for the retrofit team; it never ships as a /command to end users.
- Real-time scoring during retrofit runs — post-hoc only; mixing producer and grader in the same run defeats the purpose.
- Replacing human review for tricky cases — LLM judge reports confidence; low-confidence cases route to human, not silently accepted.
- Per-language grading splits — start language-agnostic; split only if systematic per-language failure modes emerge.
- Grading retrofit-skill's prompt iterations in CI as a merge gate — defer; flaky grader as a merge gate is worse than no gate.
- Building our own LLM eval framework from scratch when promptfoo/deepeval/Inspect exist — at least seriously evaluate wrapping an existing framework before reinventing (see Open Questions).

## Key Assumptions to Validate

| Tier | Assumption | How to validate |
|------|------------|-----------------|
| Must-be-true | Ensemble LLM-as-judge (Claude + GPT-4o + Gemini, majority vote) reaches Cohen's κ ≥ 0.6 against human labels on AC-equivalence, OR reaches the inter-human ceiling, whichever is lower. Raw percentage agreement is reported as a sanity check but is not the success metric. Periodic gold-standard against fresh human labels detects ensemble collusion | Sample 200 AC pairs from the calibration corpus; have 2 humans independently grade equivalence (measures inter-human κ as ceiling); run the ensemble judge; report Cohen's κ for ensemble vs each human and against the human consensus |
| Must-be-true | Hierarchy-aware bipartite matching (source-pointer Jaccard + embedding cosine + tree-structural alignment) produces stable Feature pairings; matcher precision and recall each ≥ 0.8 against human-identified pairings | Manually identify ground-truth ↔ retrofit Feature pairings on the calibration corpus (including hierarchy position); measure precision and recall of the matcher |
| Must-be-true | Score deltas across retrofit prompt iterations are *informative* on the train corpus AND generalize to the held-out test corpus — generalization is the load-bearing claim, not in-distribution discrimination | Run 5 prompt-iteration cycles on the *train* corpus; measure train-set delta-ordering vs human ranking (≥80% pairwise agreement); then evaluate the best-of-5 against the held-out corpus to confirm the improvement generalizes |
| Must-be-true | Cross-model ensemble (not just "different model") + adversarial set + periodic human gold meaningfully reduces shared-blind-spot risk vs a single judge from a different family. Frontier models share enough pretraining and RLHF preference structure that "different family" alone is insufficient | Plant known-wrong outputs in the corpus; verify ensemble catches them; compare single-judge vs ensemble on a held-out sample |
| Must-be-true | Position bias is controlled: swap-test confirms that pairwise judgments are stable across order (≥90% same verdict when A and B are swapped). Single-order judgments are not used as scores | For 100 sampled pairs, run the judge with both orderings; measure the agreement rate; reject pairs that flip on swap (or treat as "uncertain") |
| Must-be-true | Calibration corpus of **≥5 repos producing ≥200 graded AC pairs** is enough to produce statistically meaningful inter-iteration deltas with bootstrap confidence intervals reported. Below this threshold, score noise swamps signal | Source/build the 5-repo corpus before week 1; measure standard error on Coverage / faithfulness; verify SE << observed deltas |
| Must-be-true | The judge independently verifies entailment from cited source pointers regardless of the AC's `derived-from` trailer. Provenance trailers are producer-controlled metadata; the grader cannot trust them as ground truth | Plant ACs labeled `derived-from: test` where the cited test does *not* entail the assertion; verify the judge flags these as unsupported |
| Should-be-true | Test-retest reliability of the ensemble judge (n=3 runs, temperature=0, pinned model versions): median agreement varies by ≤8% across runs; report median + IQR rather than chasing tighter bounds | Run the ensemble 3× on the same calibration corpus; report median + IQR for each scoring dimension |
| Should-be-true | DLP scrub effectiveness can be graded against a planted-secrets corpus with realistic distribution (API keys, tokens, internal hostnames, customer-id patterns) — precision and recall both meaningful | Plant 50 known secrets across the calibration corpus at varying obscurity; measure scrub recall (caught / planted) and precision (true-positive / scrub-redacted) |
| Should-be-true | The wrap-vs-build decision (Inspect / promptfoo / deepeval / in-house) can be made on a 2-day spike that produces a representative working evaluator end-to-end | Time-box the spike per framework; measure delivery time vs feature coverage |
| Might-be-true | Embedding-based Feature matching produces stable enough pairings across model versions that retrofit-evaluation results are reproducible over time | Defer to v1.1; if embeddings drift across model updates, switch to a frozen embedding model or revert to string-based matching |
| Might-be-true | Held-out test corpus of 1-2 repos (out of 5+) is enough to detect train/test overfit. May need a larger held-out fraction if iteration count grows | Defer; revisit after first held-out evaluation reveals (or fails to reveal) train/test divergence |


## SpecScore Integration

- **New Features this would create:** `retrofit-evaluation-skill` (one parent Feature; likely subdivided at spec time into `feature-matching` (Coverage), `ac-equivalence-grading` (AC faithfulness), `hallucination-detection`, `structural-grading`, and `report-generation`).
- **Existing Features affected:** Closes the feedback loop on `retrofit-skill`. May share AC-equivalence judge prompts with `specify`'s reviewer-gates Feature (both ask "are these ACs equivalent / faithful?"). Could also be repurposed to grade `survey-skill` output (architecture summary accuracy) — out of scope for retrofit-evaluation MVP but a natural extension.
- **Dependencies:**
  - `retrofit-skill` MVP must exist with calibration mode (`--ignore-existing-specs --output-dir`) shipped.
  - Ground-truth calibration corpus must exist — at minimum `specstudio-skills` (already has Features) plus one external repo with hand-written SpecScore specs.
  - An LLM provider with a model tier different from retrofit's coordinator/researcher models (cross-model judging discipline).
  - Optional: an existing eval framework (Inspect / promptfoo / deepeval) — see Open Questions; if adopted, becomes a hard dependency.

## Open Questions

**Assumed choices, recorded for review** (best-judgment defaults made because the user is away; flag any to override):
- *Build vs wrap — DECIDED.* Spike Inspect (UK AISI, 2 days) and promptfoo (1 day) in parallel before week 1 of eval MVP. Default to **promptfoo** at spike-end unless Inspect demonstrates a clear advantage — promptfoo's native pairwise + position-bias swap test maps directly to the eval design. Deepeval ruled out (vendor-leaning posture; don't want to be on a roadmap controlled by a hosted-product company). In-house build is the fallback only if both spikes fail.
- *Cross-model judging.* Assumed judge uses a *different model family* (or at minimum a different size tier) than retrofit. E.g. if retrofit uses Sonnet for the coordinator, the judge uses GPT-4o or Gemini, or at minimum Opus, to avoid shared blind spots.
- *Report storage — DECIDED.* Reports live at `.specscore/eval/<corpus-slug>-<iso-date>.{md,json}` (hidden, NOT committed). Eval output is internal to the retrofit team's iteration loop, not user-facing; committing every iteration's report would bloat the repo and clutter PR reviews. Regression tracking is solved via `.specscore/eval/history.jsonl` — one append-only summary line per run capturing the headline scores and timestamp, suitable for plotting and trend detection without checking in the full reports.
- *Failure-mode classification.* Assumed reports include a "common failure modes" section auto-clustered across the corpus (e.g. "Feature 'auth middleware' consistently mis-named 'authentication'") to drive prompt iteration. May or may not be useful — confirm at spec time.
- *Threshold for "ship-ready" retrofit.* Assumed retrofit ships when Coverage precision ≥ 0.7, Coverage recall ≥ 0.7, AC-faithfulness κ ≥ 0.6 (or inter-human ceiling), Hallucination rate ≤ 10%, DLP-scrub recall ≥ 0.9 against planted-secrets corpus. These numbers are placeholders — calibrate against real iterations before locking.
- *Naming.* Assumed the canonical user-facing slug remains `retrofit-evaluation-skill` for this Idea's lifecycle, but the eventual specstudio skill verb is **`specstudio:grade`** (single-verb house style, matches `ideate`/`specify`/`plan`/`implement`/`verify`/`recap`). Family review flagged the current compound name violates the house style. Renaming the Idea slug now would invalidate the cross-Idea references in `retrofit-skill.md` and `survey-skill.md`; defer the file rename to spec time.

**Genuine opens (no assumed answer):**
- **Adversarial-set rotation.** Planted-bug patterns become known to the prompt-iteration team over time, neutralizing their tripwire value. Proposed mitigation: rotate the active adversarial set each release, keep the active set out of the train corpus, archive retired adversarials for regression tracking only. Frequency, generation procedure, and rotation discipline are open.
- **Calibration-corpus assembly ownership.** Eval requires a 5-repo / ≥200-AC-pair corpus to ship MVP. Retrofit's own MVP only commits to 2 repos. The 5-repo corpus is **eval's blocker**, not retrofit's — assembly (sourcing repos, writing or curating ground-truth specs, adding `Verifies:` trailers, planting secrets and distractors for DLP grading) is part of eval's MVP scope and starts in parallel with retrofit's MVP, not sequentially after. Add a dedicated week-0 corpus-assembly task to eval's 3-week timeline.
- Calibration corpus growth — beyond the MVP 5-repo set, what does v2 look like? Curated synthetic repos with deliberately tricky cases (cross-cutting concerns, monorepo, polyglot)? Real-world repos from open source? Repos contributed by users (with their ground-truth specs)?
- Privacy: calibration repos may include ground-truth specs from private codebases shared with the retrofit team but not publishable. How does the team store and version these? Separate private repo? Encrypted bundle?
- LLM judge prompt versioning — pinned per retrofit-evaluation release, or free-running? Pinned gives reproducibility; free-running tracks judge improvements. Probably pin per release, surface diffs in the report.
- Cost — running 5+ iterations of retrofit-evaluation against the corpus could become expensive (judge calls per AC × ACs × iterations × corpus). Budget modeling needed at spec time.
- Does retrofit-evaluation also grade survey-skill output (architecture summary accuracy, zone proposal quality)? Probably yes but as a separate dimension or separate run; out of scope for MVP.
- Should retrofit-evaluation produce *prescriptive* suggestions ("retrofit consistently misclassifies validation Features — consider adding examples to the AC-derivation prompt")? Or just descriptive scores and let humans interpret? MVP leans descriptive; prescriptive is a stretch goal.
- CI integration — eventually retrofit-evaluation should run against retrofit's calibration corpus on every retrofit prompt change. Defer to post-MVP; the Not-Doing item is explicit.
- Statistical confidence — single-corpus scores are point estimates with unknown variance. Should reports include bootstrap CIs? At what corpus size does that become meaningful?
- How does retrofit-evaluation handle ACs in retrofit output that have *no* ground-truth counterpart (retrofit hallucinated a Feature that doesn't exist in ground truth)? Counted in Hallucination rate? Coverage? Both?
- The internal-only positioning — is "internal" enforced via skill description ("not pitched to users") or via plugin packaging (excluded from the public specstudio plugin)? Different mechanisms.
- ~~Naming~~ — *defaulted to `specstudio:grade` for the eventual specstudio skill verb (see Assumed choices above); file slug rename deferred to spec time to avoid invalidating cross-Idea references.*
- Internal-only enforcement mechanism — `retrofit-evaluation` is internal-facing (not pitched to end users), but lives in the same plugin registry as user-facing skills. Three options: (1) exclude from the public `specstudio` plugin package (build-time gate); (2) tag with an internal-only frontmatter and have the skill loader hide it from end-user discovery; (3) accept honor-system (skill description says "internal" and that's it). Preferred: (1) — build-time exclusion is the only enforcement that survives accidental discovery. Resolve at spec time.
